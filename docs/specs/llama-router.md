# Spec: llama-server router (presets, load/unload, builds, migration)

> **Status:** approved design · **Epic:** E2 · **Code:** `agent/internal/router/` · **Doctor area:** `LAI-LLM`
> Canonical names: [overview.md](../architecture/overview.md) §3. Decision: [ADR-0002](../decisions/0002-llama-router-mode.md). Catalog schema: [catalog.md](catalog.md). Agent API: [agent.md](agent.md) §3.8.
> Verified against llama.cpp commit **`f3586e66b`** (2026-10-31): `tools/server/README.md` §"Using multiple models", `tools/server/server-models.cpp`, `common/preset.cpp`, `common/arg.cpp`. Any statement below about router behaviour must be re-verified when the pinned commit changes (§9.3 test R1–R8).

## 1. Purpose and scope

Every node serves its LLMs and VLMs through one `llama-server` process in **router mode** on `127.0.0.1:8080`, unit `localai-llama.service`. This spec defines:
- the exact systemd unit (router mode, and the `single` fallback);
- how the agent **generates** `/etc/localai/models.ini` from the catalog, the profile and `node.yaml`;
- the **fit rules** that decide whether a model may be loaded;
- the **load/unload orchestration** (eviction, readiness, timeouts, rollback);
- which model is loaded at boot;
- how llama.cpp is **built** into `/opt/localai/llama.cpp/builds/<commit>-<backend>` and switched;
- the **migration** from today's hand-made `llama-qwen.service` with zero client changes;
- the `/v1/models` output the gateway relies on;
- the benchmark helper `aictl bench`.

### Non-goals
- Downloading model files (that is [ark-sync.md](ark-sync.md); the router's own `-hf`/`POST /models` download feature is **never** used).
- Choosing which models a profile contains ([catalog.md](catalog.md)).
- whisper.cpp and piper ([companion-services.md](companion-services.md)).
- Per-request routing across nodes ([gateway.md](gateway.md)).
- ROCm/HIP builds (AMD nodes use Vulkan RADV, as on ai-n1 today). A future ADR may add `rocm`.

## 2. Concepts

| Term | Meaning |
|---|---|
| **Router** | `llama-server` started without `-m`. It spawns one child `llama-server` per loaded model on a random loopback port and forwards requests by the `model` field |
| **Preset** | One INI section `[<model-id>]` in `models.ini`. Keys are llama-server args without dashes |
| **Effective model set** | The llama models that get a preset on this node (§4.1) |
| **Loaded set** | Models whose router status is `loaded` or `loading` (and `sleeping`, which we never enable) |
| **Static fit** | Can this model ever load on this hardware? Drives `loadable` in the API |
| **Dynamic fit** | Can it load **now**, given what else is loaded? Drives eviction |
| **Build id** | `<commit>-<backend>`, e.g. `f3586e66b-cuda`. `commit` is the 9-char short sha (`git rev-parse --short=9`) |
| **Legacy alias** | An extra model name kept from the pre-migration unit (e.g. `qwen3.5-9b`), so old clients keep working |

### 3.2 `localai-llama.service` (router mode)

Generated from a Go template (`internal/router/unit.go`). Values in `<>` come from the profile; everything else is fixed. Example for ai-n3 (profile `small-8gb`: `models_max: 1`, `memory_margin_mib: 512`):

```ini
# GENERATED by aiagent — do not edit. Regenerated from node.yaml + catalog profile.
# Spec: docs/specs/llama-router.md §3.2
[Unit]
Description=Local AI llama.cpp router (llama-server, router mode)
Documentation=https://github.com/marinoscar/local-ai/blob/main/docs/specs/llama-router.md
After=network.target local-fs.target
StartLimitIntervalSec=300
StartLimitBurst=5

[Service]
Type=simple
User=localai
Group=localai
SupplementaryGroups=video render
WorkingDirectory=/var/lib/localai
LoadCredential=llama-api-key:/etc/localai/api-key
Environment=LLAMA_CACHE=/var/lib/localai/llama-cache
ExecStart=/opt/localai/llama.cpp/current/bin/llama-server \
  --models-preset /etc/localai/models.ini \
  --models-max <1> \
  --models-memory-margin <512> \
  --no-models-autoload \
  --host 127.0.0.1 \
  --port 8080 \
  --api-key-file %d/llama-api-key
Restart=on-failure
RestartSec=5
TimeoutStartSec=60
TimeoutStopSec=30
LimitMEMLOCK=infinity
# Hardening that does not interfere with GPU access or mmap of model files:
NoNewPrivileges=yes
PrivateTmp=yes
ProtectSystem=strict
ProtectHome=yes
ReadWritePaths=/var/lib/localai
ProtectKernelTunables=yes
ProtectKernelModules=yes
ProtectControlGroups=yes
RestrictSUIDSGID=yes
LockPersonality=yes

[Install]
WantedBy=multi-user.target
```

Rules:
- **No per-model args on the router command line.** Router CLI args have the highest precedence and are inherited by every child (README §Model presets, precedence rule 1). Anything model-specific goes in the preset.
- `--models-memory-margin` is emitted only when the profile's `memory_margin_mib > 0`. It turns on the router's own LRU memory check; the agent's fit rules (§4.3) run first, so the router's check is a second line of defence. A profile that leaves the field unset (0) therefore gives no flag, while the fit rules still reserve their default margin (§4.3.1): the two readings of "unset" are deliberate. `models_max` below 1 is rendered as 1, as the fit rules count it.
- The unit is **the same for every backend** (CUDA, Vulkan/ROCm, CPU): the backend is what the binary under `current/` was built with (§4.10), and backend-specific variables (`GGML_VK_*`, `CUDA_*`) go in the drop-in (§3.3), never in the unit.
- The unit carries no time, version or hash, so two renderings of the same inputs are byte-identical and the file is compared as a whole.
- `ProtectSystem=strict` makes `/srv/localai` and `/media/*` read-only for llama, which is what we want (models are only read). `ProtectHome=yes` is safe because after migration no model lives under `/home`.
- `PrivateDevices` and `MemoryDenyWriteExecute` are **not** set: GPU device nodes must be visible, and the CUDA/Vulkan drivers JIT code.
- `KillMode` stays the default `control-group`, so stopping the unit also stops every child instance.
- `WantedBy=multi-user.target`: llama starts at boot **without** the agent. Inference survives a broken agent.

### 3.3 Environment drop-in

`/etc/systemd/system/localai-llama.service.d/50-env.conf`, generated when the merged environment (§4.2 step 6) is non-empty:
```ini
# GENERATED by aiagent — do not edit. Spec: docs/specs/llama-router.md §3.3
[Service]
Environment=GGML_VK_SUBALLOCATION_BLOCK_SIZE=4294967296
```
Preset files cannot carry arbitrary environment variables (unknown INI keys are rejected by `common/preset.cpp`), and children inherit the router's environment, so per-model `llama.env` from the catalog is merged here. Changing this file requires a router restart; the agent does not restart automatically, it raises `LAI-AGT-016` ("restart llama to apply").

### 3.4 `localai-llama.service` (`single` fallback mode)

When `node.yaml: llama.mode: single` (ADR-0002 risk mitigation), the same unit name runs a classic one-model server for the **current default model**. Same `[Unit]`, `[Install]` and hardening as §3.2 (the `Description` still says "router mode"; `LAI-LLM-023` tells the operator which mode is active); only `ExecStart` differs. ai-n3 example:
```ini
ExecStart=/opt/localai/llama.cpp/current/bin/llama-server \
  -m /srv/localai/models/qwen3.5-9b-q4km/Qwen3.5-9B-Q4_K_M.gguf \
  --alias qwen3.5-9b-q4km,qwen3.5-9b \
  --tags chat,reasoning,coder \
  -c 32768 \
  -ngl 99 \
  --flash-attn on \
  --parallel 1 \
  --spec-type draft-mtp \
  --spec-draft-n-max 3 \
  --host 127.0.0.1 \
  --port 8080 \
  --api-key-file %d/llama-api-key
```
The args come from the same mapping table (§3.5.1). Each INI key is rendered through this key → CLI flag table (keys not listed render as `--<key> <value>`; keys with value `true` render as the bare flag):

| INI key | CLI flag |
|---|---|
| `model` | `-m` |
| `c` | `-c` |
| `n-gpu-layers` | `-ngl` |
| `alias` | `--alias` |
| any other key `k` | `--k` |

The example above is the exact expected rendering (short flags `-m`, `-c`, `-ngl`). Order: `-m`, then `--alias` and `--tags`, then the remaining keys in the order of the mapping table (§3.5.1). `--alias` lists the model id first (there is no section name in single mode, and clients ask for the id) and then the node's `legacy_aliases`; an alias that is not valid, contains a comma or equals the id is left out and reported (`LAI-LLM-007`, subject `alias:<a>`). A key of one character is a short flag (`b` → `-b`), and so are the short-only spellings a catalog `extra_args` entry can use without dashes (`ub`, `ctk`, `ctv`, `ctkd`, `ctvd`, `np`, `ts`, `sm`, `mg`, `md`, `ngld`, `fa`, `nkvo`, `cb`): the INI key drops the dash, and `--ub` would not be a llama-server flag. `load-on-startup` and `stop-timeout` are router-only and never rendered. The argv is never passed through a shell: a word with white space, a quote, a backslash or `;` is written in double quotes with each backslash and double quote escaped by a backslash, and `%` and `$` are doubled (systemd expands both in unit files), so a drive mounted under `/media/user/My Drive` works. In single mode, "load model X" means: rewrite the unit for X, `daemon-reload`, restart, wait for `/health` 200 and `/v1/models` listing X, and roll back to the previous unit on failure (§4.8).

#### 3.4.1 How the unit is rendered and written (`internal/router`, ROUTER-04)

`router.RenderUnit` (`unit.go`) is pure: a `text/template` for §3.2 with `ExecStart` filled from the profile (`UnitInputs.Router`) or, in single mode, from `router.BuildPreset` of the model (`UnitInputs.Single`) through `router.SingleFlag`. It refuses what cannot be a unit (`router.UnitError`): a binary path that is not a clean absolute path of letters, digits and `. _ + - /`, a port outside 1..65535, an unknown mode, a single-mode model that cannot be a preset (§3.5.4). `router.UnitGenerator.Generate` brings the disk to it:

1. Make sure `/var/lib/localai/llama-cache` exists (parents 0755, the directory localai:localai 0750; a wrong mode or owner is corrected) and count what it holds. A directory that is **not empty** raises `LAI-LLM-024` (subject `llama-cache`, details `entries` and up to five `names`) and **nothing in it is deleted**; the alert clears when the operator has emptied it. A path that is not a directory, or a failed mkdir, chmod, chown or read, is `LAI-LLM-007` (subject `llama-cache`). None of this stops the unit from being written.
2. Check that the binary exists, is a regular file and is executable; if not, `LAI-LLM-002` (subject `binary`, `details.reason`: `missing` (also a broken `current` symlink), `not_a_file`, `not_executable`, `stat_failed`). The unit is still written: it names the right path either way, and the build manager may be about to install the build.
3. Render. A render error is `LAI-LLM-007` (subject `unit`) and the existing unit is left alone: a working unit is never replaced by one that cannot work. In single mode the model's files must be readable by the unit's user (`router.CheckReadable`, as §4.2 step 3); if not, `LAI-LLM-008` (subject: the model id), an error, and the unit is untouched.
4. Read the current file. If its sha256 differs from `state.llama.unit_sha256` (someone edited it), save it as `localai-llama.service.hand-edited-<ts>` (`-2`, `-3` ... when taken) and raise `LAI-LLM-006` (subject `unit`, `details.file: unit`), with the same refinements as §4.2 step 4: with no recorded hash a file that starts with `# GENERATED by aiagent` is ours and any other is saved; a file that already holds the new rendering loses nothing and is not reported; if the copy cannot be written the file is not overwritten (`LAI-LLM-007`, an error).
5. If the bytes are identical, do not write (the recorded hash is corrected if stale). Otherwise keep the old file as `localai-llama.service.prev`, write the new one atomically (`config.WriteFileAtomic`: temp file, fsync, rename, directory fsync; root 0644) and record the sha256 of the file as written in `state.llama.unit_sha256`. A write that fails (unwritable or read-only directory, `ENOSPC`, rename) leaves the old file and the hash untouched: `LAI-LLM-007` (subject `write unit`), an error returned. An `ErrNotDurable` (only the directory sync failed) counts as written.
6. `daemon-reload` through the services manager **only when the file was written**. A failed reload is `LAI-LLM-007` (subject `daemon-reload`) in the result, and the next run reloads again although the file is unchanged. (After an agent restart the startup sequence of AGENT-20, regenerate then reload, covers it.)
7. `router.RestartRequired(old, new)` compares the `[Service]` section of the old and the new file (comments, blank lines, line wrapping, `[Unit]` and `[Install]` do not count; repeated directives compare in order); a difference means the running llama still has the old command line, environment or limits. `Result.RestartRequired` and `Changed` (directive names) are set and `LAI-AGT-016` is raised (`target: llama`, `reason: unit`). The generator never restarts llama: the operator does, or ROUTER-07 in the single-mode load. A first write, or a rewrite with identical `[Service]` directives, needs none.

While the unit is in single mode `LAI-LLM-023` (info) is raised, and cleared when router mode is back. Findings are raised through the alert sink and cleared when a later run no longer finds them; `LAI-LLM-006` and `LAI-AGT-016` are events, as for `models.ini`. The environment drop-in is **not** written here: `Generator` (§4.2 step 6) owns it and runs `daemon-reload` for it. A pass that changes both therefore reloads twice, which is harmless.

**Golden files.** `internal/router/testdata/golden/localai-llama.router.service` (ai-n3: `--models-max 1 --models-memory-margin 512`), `localai-llama.router.ai-n1.service` (`--models-max 3 --models-memory-margin 2048`), `localai-llama.single.service` (§3.4) and `50-env.conf` (§3.3, the drop-in of a Vulkan node). A test renders the unit examples of §3.2 and §3.4 from this file's own code blocks and compares them, so the spec and the generator cannot drift. `scripts/verify-units.sh` runs `systemd-analyze verify` on all four files (the `units-verify` workflow); regenerate the goldens with `go test ./internal/router -run 'Unit|DropIn' -update` and read the diff.

### 3.5 `models.ini` (preset file)

#### 3.5.1 Mapping table: catalog / node → INI keys

| Source | INI key in `[<id>]` | Rendering rule |
|---|---|---|
| `models[].id` | section name `[<id>]` | the section name **is** the router model name and the OpenAI `model` id (ADR-0002) |
| `files[kind=weights]` | `model` | absolute path on the chosen content root (§4.1): `<root>/models/<id>/<name>`. Multi-shard: the `-00001-of-NNNNN` file |
| `llama.ctx` | `c` | integer. Always pinned (so `--fit` cannot grow the context and starve other models; README §Memory-based unloading) |
| `llama.n_gpu_layers` | `n-gpu-layers` | integer, or `all` |
| `llama.flash_attn` | `flash-attn` | `on` \| `off` \| `auto` |
| `llama.parallel` | `parallel` | integer |
| `llama.speculative.type` | `spec-type` | `draft-mtp` \| `draft` |
| `llama.speculative.n_max` | `spec-draft-n-max` | integer |
| `llama.speculative.draft_file_kind` (non-null) | `model-draft` | absolute path of `files[kind=draft]` |
| `llama.speculative.draft_ngl` | `spec-draft-ngl` | only when `model-draft` is emitted; `all` or integer |
| `llama.mmproj_file_kind` (non-null) | `mmproj` | absolute path of `files[kind=mmproj]` |
| `llama.chat_template` = builtin name | `chat-template` | string |
| `llama.chat_template` = a file kind | `chat-template-file` | absolute path of that file |
| `llama.extra_args[]` | one key per arg | `--foo bar` → `foo = bar`; `--foo` (flag) → `foo = true`; `--no-foo` → `no-foo = true`; `-x v` → `x = v`. The linter (catalog.md §2) already refuses host/port/api-key/model/models-*/alias/-hf |
| `roles[]` | `tags` | comma-joined in catalog order, e.g. `chat,reasoning,coder`. Informational in `/v1/models` |
| `node.yaml: llama.legacy_aliases[<id>]` | `alias` | comma-joined. The router registers them as routing aliases (`server-models.cpp`: aliases parsed from the preset's `alias`, conflict-checked against other names) |
| effective default model (§4.6) | `load-on-startup` | `true` in the default model's section only |
| fixed | `stop-timeout` | `10` in `[*]` |
| fixed | `load-on-startup` | `false` in `[*]` |
| `llama.env` | — | **not in INI**; merged into the drop-in §3.3 |
| `requirements.*`, `client_hints.*`, `summary*` | — | not rendered (used by fit rules, snippets and the gateway) |

Rendering is deterministic: sections sorted by model id (default first is **not** used, to keep diffs stable); keys in the table order; values never quoted; paths are validated to contain no `;`, `#`, newline or leading/trailing spaces (else `LAI-LLM-007`).

#### 3.5.4 How the file is rendered (`internal/router`, ROUTER-03)

`router.BuildPreset` renders one model's section, `router.Render` the file, `router.MergeEnv` and `router.RenderDropIn` the drop-in. They are pure; `router.Generator` (§4.2) wraps them with the disk, the state store and the router. The rules the mapping table leaves open:

- **Which file.** `files[kind=K]` is the one file of kind `K`. A model that lists several files of one kind (the shards of a split GGUF) is given the one whose name ends in `-00001-of-NNNNN.gguf`; several files and not exactly one first shard is an error (`LAI-LLM-007`). A file name must be a clean relative path (no leading `/`, no `..`, no `./`): the preset never points outside `<root>/models/<id>/`.
- **Which keys.** A key is written only when its catalog field is set: `n_gpu_layers: 0` is written (`n-gpu-layers = 0`), an absent `n_gpu_layers` is not. `spec-draft-n-max` is written only when `n_max` is above 0. `llama.speculative.draft_ngl` is written only together with `model-draft`. `llama.mmproj_file_kind` and `draft_file_kind` name the *kind* of the file to look up, so a catalog that names a kind it has no file for is an error.
- **`extra_args`.** Each list entry is split at its first space or `=`; an entry that is not a flag is the value of the previous flag (`["--temp", "0.7"]` equals `["--temp 0.7"]`; a negative number is accepted there as a value). The key is the flag without its one or two leading dashes, so `-ub 512` gives `ub = 512`. A flag without a value is `true`. The agent refuses again what lint refuses (host, port, `api-key*`, `-m`, `--model`, `--models-*`, `--alias`, `-hf`), and also the keys it writes from other fields (`model-*`, `mmproj*`, `tags`, `load-on-startup`, `stop-timeout`, `version`) and a key that duplicates one the section already has (`-c 8192` next to `ctx`): an unsafe or ambiguous entry makes the model's section fail, not the file.
- **Unsafe text.** A path, an alias or an `extra_args` value containing `;`, `#` or a control character is refused, as is a path that is not absolute or has leading or trailing white space. Header values (node id, profile id, catalog version) are reduced to letters, digits and `. _ - : +` so they cannot break out of the comment line.
- **Aliases.** `legacy_aliases[<id>]` becomes `alias`. An alias that is not a valid name, equals a section name or is already taken by a model that sorts earlier is left out and reported as `LAI-LLM-007` (`details.alias`), because the router checks aliases for conflicts and a refused file would leave every model unloadable. An alias of a model that is not in the file is ignored.
- **`inputs_sha256`** is the sha256 of the canonical JSON (fixed field order, sorted map keys and lists, no HTML escaping) of: the renderer version, node id, profile id, catalog version, the profile overrides' add and remove lists, the effective default, and for every model in the file its id, chosen root, roles, `llama` block without `env`, file kinds and names, and aliases. It therefore changes when a section changes and not when a field the table does not render changes (a summary, a `client_hints`, a `llama.env`).
- **Comparison.** Two renderings are compared without their first line (time and agent version). Everything else, including the `inputs_sha256` line, is compared.
- **Golden files.** `internal/router/testdata/golden/ai-n3.models.ini` and `ai-n1.models.ini` hold the files of §3.5.2 and §3.5.3 as `Generator` renders them for those catalogs, with a fixed clock, so even the first line is byte-identical. The one value a golden file cannot hold is the 64-hex hash (a digest-shaped literal trips the secret scanners), so the test replaces it with `<sha256>` in both sides before comparing and checks the hash separately. Regenerate with `go test ./internal/router -run Golden -update` and read the diff.

**Environment drop-in.** `MergeEnv` takes the models that are in the file (a model that was dropped contributes nothing) and `node.yaml llama.extra_env`. The node's value wins, even over a conflict. `LLAMA_ARG_*` is refused from both sources (the router sets those; an inherited one would override its arguments), as is a name that is not valid (catalog: any environment variable name; node: `^(GGML|LLAMA|CUDA)_[A-Z0-9_]+$`) and a catalog value that is not one line. A refusal is `LAI-LLM-007` with `details.source`; a refused value is never recorded. `RenderDropIn` writes `Environment=NAME=value` lines sorted by name; a value with white space, quotes or a backslash is written as `Environment="NAME=value"` with those escaped, and `%` is doubled (systemd expands specifiers in unit files).

### 3.6 Router API used by the agent

All calls go to `http://127.0.0.1:8080` with `Authorization: Bearer <key>` (every route except `/health` requires the key, `server-http.cpp` public endpoint list). HTTP client timeout 5 s per call unless stated.

| Call | Purpose | Notes |
|---|---|---|
| `GET /health` | liveness | public (`/v1/health` too); `200 {"status":"ok"}`, or `503` with an error object while the model of a single-mode server is loading |
| `GET /models` | status of every preset | `data[].id`, `aliases`, `tags`, `status.value` ∈ `unloaded\|loading\|loaded\|sleeping\|downloading\|incomplete`, `status.failed`, `status.exit_code`, optional `memory.{min,max,effective}` (with `--models-memory-margin`) |
| `GET /models?reload=1` | re-read `models.ini` and reconcile | a **running** model whose preset changed or was removed is **unloaded** by the router (`server-models.cpp` reload path). See the reload-safety rule §4.2 step 8 |
| `POST /models/load` `{"model": "<id>"}` | start a child | returns `{"success": true}` immediately; readiness is observed via `GET /models` |
| `POST /models/unload` `{"model": "<id>"}` | stop a child | child gets `stop-timeout` (10 s) then is force-killed |
| `GET /models/sse` | progress events (`model_status` / `status_change` with `progress.stages/current/value`) | optional; used for UI progress and to nudge the watcher, never for correctness. Frame format in §3.6.1 |
| `GET /v1/models` | the OpenAI list | in router mode this is the same handler as `/models` |
| `GET /props?model=<id>` | `n_ctx`, build info of a loaded model | doctor checks only |
| `POST /v1/chat/completions` | doctor/drill smoke test | `max_tokens: 8` |

Never used: `POST /models` (download), `DELETE /models`, `?autoload=true`.

#### 3.6.1 The client (`internal/router`, ROUTER-01)

The wire facts below were checked against `tools/server/README.md`, `server-models.cpp` and `server-http.cpp` at llama.cpp commit `f3586e66b`; the manual checks R9 and R10 (§9.3) re-verify the two that matter most after a commit change.

**Shapes.**
- `status.value` is one of `unloaded`, `loading`, `loaded`, `sleeping`, `downloading`, `downloaded`, `incomplete`. A value outside the list is kept as is and treated as "not running" (logged once per change); it is never a parse error, so a llama.cpp upgrade cannot blind the watcher.
- `status.failed: true` and `status.exit_code` appear **only** when the model is not running and its child exited with a non-zero code (the router's `is_failed`). A model that was never started has neither.
- `status.args` is the child's command line (no key: the router strips it); `status.preset` is the INI section text; `status.progress` is, for a downloading model, a map `URL → {done, total}`. Loading progress is **not** in `GET /models`, only on the SSE stream.
- `source` is `preset`, `models_dir` or `cache`; `aliases` and `tags` are lists; `context_length` is the training context. `architecture.{input,output}_modalities` are lists of strings.
- `memory` exists only with `--models-memory-margin`: `{status, min, max, effective}`, each estimate `{n_ctx, devices: [{kind: "device"|"host", name, total, free, model, context, compute}]}` in **bytes**; `effective` is `null` unless the model is loaded. The planner's `used_v(k)` is the sum of `model + context + compute` over the entries of kind `device`, rounded up to MiB (`ModelStatus.EffectiveMiB`); the `host` entry is RAM and is ignored.
- Decoding is strict about shape (a body that is not an object with a `data` array, an entry without `id` or `status.value`, a duplicate id, a wrong type, a negative size, trailing data, a body over 8 MiB: `ErrMalformed`) and tolerant about content (unknown fields and unknown values are ignored).
- Errors are `{"error": {"code", "message", "type"}}`. `POST /models/load` of a running model is `400` ("model is already running"), of an unknown model `404`; `POST /models/unload` of a model that is not running or unknown is `400`. A wrong or missing key is `401` ("Invalid API Key", `authentication_error`).
- SSE: `Content-Type: text/event-stream`, one `data: <json>` line plus a blank line per event, **no** `event:` line. The JSON is `{"model": "<id>" | "*", "event": "<name>", "data": {...}}`. Names seen: `model_status` (the first, at spawn), `status_change` (every later change; `data.status`, `data.exit_code` with `unloaded`, `data.progress {stages, current, value}` while loading), `download_progress`, `download_finished`, `download_failed`, `model_remove`, `models_reload` (model `*`), `model_memory`. The README documents `model_status` only; the client treats `model_status` and `status_change` alike and skips a frame it cannot use without ending the stream. A line over 1 MiB ends the stream.

**Rules.**
1. **Base URL and key.** `http://127.0.0.1:<llama.port>`; the client refuses any base URL that is not plain `http` on a loopback address (no credentials, path or query). The key is read from `/etc/localai/api-key`, re-read when the file's mtime or size changes, after `key.rotated` and after a `401` (§4.11), and sent only as `Authorization: Bearer`. `/health` is sent without it. The key never appears in a log line, an error, an event or a finding: logs carry its fingerprint (last four characters). A key file that is missing, not a regular file or holds an unusable value fails the call before anything is sent.
2. **A `401` is retried once**, and only when re-reading the key file gives a different key (the key was rotated between two reads). An unchanged key is a real `401`: `LAI-LLM-005`, never retried.
3. **Transport hardening.** The proxy environment is ignored; the dialer connects only to loopback addresses; a redirect is never followed (it is an error); response bodies are capped (8 MiB for `GET /models`, 1 MiB otherwise); compression is off.
4. **Timeouts.** 5 s per call; `POST /v1/chat/completions` (the smoke test) 30 s, because it generates tokens and a CPU node is slow; the SSE stream has no overall timeout, only 5 s to receive its headers.
5. **Error classes.** Connection refused or reset, a timeout, or `502`/`503`/`504` is `ErrDown` (`LAI-LLM-004`); `401` is `ErrUnauthorized` (`LAI-LLM-005`); `404` is `ErrNotFound`; any other non-2xx is an `*HTTPError` with the router's message (scrubbed, at most 200 bytes); an unusable body is `ErrMalformed`. A call cancelled by its caller returns the context error, not `ErrDown`.
6. **Allow list.** The client can issue only the routes of the table above. A download (`POST /models`), a delete (`DELETE /models`) and any `autoload` query are refused with `ErrRefused` before anything is sent; the tests assert it on the request log of the fake router.
7. **The fake.** `internal/router/fake` is a router served over HTTP with scripted model states (`Set`, `Crash`, `FailLoad`, `Restart`, load time), failure modes (`Down`, `Reset`, `Delay`, `Malformed`, `Force`, `Redirect`), a key that can be rotated, an SSE stream (`Emit`, `DropStreams`) and a request log that records method, path, query and whether a correct key was sent (never the key). Other packages' tests reuse it.

## 4. Behaviour

### 4.1 Effective model set and file location

For each catalog model `m` with `engine: llama`:
1. `m` is **in scope** if it is in the profile's `include.models` ∪ `profile_overrides.add_models` − `remove_models`, **or** it is present on any mounted content root (a stored model may still be loaded; ADR-0005 "serve directly from the drive"). `profile_overrides.remove_models` only removes `m` from the desired set (sync stops fetching it, boot does not load it); a removed model that is still present on disk **stays in scope** (it keeps a preset, is listed and loadable) until it is deleted (`aictl delete`).
2. `m` is **present** on a root if `<root>/models/<id>/MANIFEST.json` lists every `files[]` entry with matching sha256 and `verified_at` set ([ark-sync.md](ark-sync.md) §4.11). Concretely (`router.ManifestPresence`): `item_id` is the model id, `state` is `verified`, `verified_at` is an RFC 3339 time, and every catalog file has a manifest entry with the same `path` (and `kind`, when the manifest gives one) and the same sha256 (case-insensitive). A catalog file without a pinned sha256 cannot be verified, so the model is not present. Chosen root: internal (`/srv/localai`) if present there, else the first mounted ark drive (sorted by mount path); a copy on the internal root that is not verified does not hide a verified copy on a drive.
3. `m` gets a preset iff in scope **and** present **and** statically fits (§4.3.2). Others are absent from `models.ini`, so neither the WebUI dropdown nor a direct client can ask for them.

### 4.2 Preset generation (`router.Generator.Generate`)
Triggered at agent start, on catalog refresh, `PUT /profile`, `PUT /models/default`, `node.yaml` change of `llama.*`, `drive.mounted`/`drive.unmounted`, a model becoming verified or deleted, and a build switch. Calls are serialised. The caller assembles the inputs (`router.Inputs`: node id, catalog, profile, `profile_overrides`, `node.yaml llama{}`, mounted roots, the fit `Env`, `state.models.default`, survival flag); `Generate` returns an error only when `models.ini` is not in the state the inputs call for (it cannot be rendered, read, saved aside or written). A failure to apply the file to a running router, or to write the drop-in, is in the `Result` and retried by the next call.
1. Compute the effective set (§4.1) and the effective default (§4.6).
2. Render sections (§3.5.1) and the header (`inputs_sha256` = sha256 of the canonical JSON of the inputs, §3.5.4, so identical inputs give byte-identical output except the first line, which is excluded from comparisons). A model whose entry cannot be rendered (a bad catalog entry or an unsafe path, `LAI-LLM-007`) is **left out on its own**; the other models are still written.
3. Validate: every path exists and is readable by uid `localai` (`faccessat` with `AT_EACCESS` after `setfsuid` is not available in pure Go; instead check mode bits + ownership along the path: each directory from `/` down `o+x` or owned/grouped by localai with the matching bit, the file a regular file with `o+r` or owned/grouped by localai with the matching bit; `router.CheckReadable`). Failure → drop that model, `LAI-LLM-008` with `details.path` and `details.reason` (`missing`, `not_a_file`, `directory_not_searchable`, `file_not_readable`, `stat_failed`). The default (§4.6) is chosen among the models that survive steps 2 and 3, so a default that was dropped falls back to the next rule, and with none `LAI-LLM-014` is raised.
4. Read the current file. If its sha256 ≠ `state.llama.ini_sha256` (someone edited it) → save it as `models.ini.hand-edited-<ts>` (`-2`, `-3` … when the name exists) and raise `LAI-LLM-006` (warning). Refinements: with **no** recorded hash (a fresh state file), a file that carries the `GENERATED by aiagent` header is ours and a file without it is foreign and saved; a file whose body (minus the first line) already equals the new rendering loses nothing and is not reported (a crash between the rename and the state update looks like an edit); if the copy **cannot be written, the file is not overwritten** (`LAI-LLM-007`, error returned): nothing is destroyed that could not be kept.
5. If the rendered body (minus the first line) equals the current file → **do not write** (step 7 is skipped, and the recorded hash is corrected if it was stale); steps 6 and 8 still run.
6. Merge env: union of `llama.env` over models in the file, plus `node.yaml llama.extra_env` (node wins). Two models setting the same key to different values and no node value → drop the key, `LAI-LLM-015`. Render the drop-in (§3.3) and compare it with the file on disk **on every run, whether or not `models.ini` changed** (an `extra_env` edit changes only the drop-in); if it differs, write it (mode 0644; the directory is created if needed), or remove it when the merged environment is now empty, run `daemon-reload` through the systemd manager and raise `LAI-AGT-016` (details `target: llama`). The router is never restarted. A drop-in that cannot be written is `LAI-LLM-007` (`subject: drop-in`) and does not stop `models.ini`.
7. Write `models.ini` atomically (`config.WriteFileAtomic`: temp file, fsync, rename, directory fsync; root:localai 0640), keeping the previous file as `models.ini.prev` first (a failure to keep it is logged and does not stop the write), and update `state.llama.ini_sha256` (sha256 of the file as written, first line included). A write that fails (unwritable directory, `ENOSPC`, rename) leaves the old file and the recorded hash untouched and raises `LAI-LLM-007`; an `ErrNotDurable` (only the final directory sync failed) is treated as written. A state update that fails is logged; the next run recognises the file as its own and records the hash.
8. **Reload-safety rule** (pure: `router.DecideReload`). If the router is up, compare, for every model whose router status is `loaded`, `loading` or `sleeping` (`Status.Running`), the **old** and the new sections. The old sections are what the router **last read**, not necessarily what was on disk: when a reload is skipped because only `load-on-startup` differs, the router still holds the older file, so the generator keeps that older parse as the base for the next comparison (after an agent restart, or a router that was down, the file on disk before this write stands in for it).
   - only `load-on-startup` differs (a default change) or nothing differs → **do not** call reload when no section was added/removed either; the file is correct for the next router start. Otherwise reload is safe.
   - any other key differs for a running model (a change in `[*]` or `version` counts for every model) → take `modelOpsMu` (waiting up to 60 s; if it stays busy the reload is retried by the next run and the result carries the error), read the statuses again, call `GET /models?reload=1` (the router unloads that model), emit `model.unloaded {reason: "preset_changed"}` for it (with the watcher suppressed for the duration, so it is not reported twice), wait until the router has stopped it (at most 20 s), then re-load it through §4.4 while still holding the lock (`ModelLoader.LoadHeld`; until the orchestrator exists, a plain `POST /models/load`). A model that the router kept running is not loaded again.
   - a running model whose **section was removed** (its files vanished, an ark drive was pulled, it was deleted) → the same reload; the router unloads it, `model.unloaded {reason: "preset_changed"}` is emitted for it and it is **not** loaded again (it has no preset).
   - sections added or removed, or changed, only for non-running models → `GET /models?reload=1`.
   - a running model that the old file did not have (a hand edit, a lost reload) cannot be proven unchanged and is treated as changed.
   - after any reload, the models the rule meant to protect (running, section unchanged) are checked; one that the router unloaded anyway (it may judge a `load-on-startup` difference it never read as a changed preset) is reported with `model.unloaded {reason: "preset_changed"}` and loaded again.
   - **Resync.** The first run after an agent start (or after the router was seen down) compares the ids the router lists with `source: preset` (cache models are not ours) with the sections of the file; if they differ the router is reloaded even though the file did not change (the reload that should have followed the last write never happened). The same applies after a reload that failed.
9. If the router is down (`ErrDown`), nothing else to do; the next start reads the new file. Any other router error (`LAI-LLM-005`, a malformed answer) is returned in the `Result` and the apply is retried by the next run.

**Findings.** `Generate` raises through the alert sink and clears what a later run no longer finds: `LAI-LLM-007` (subjects: the model id, `alias:<a>`, `env:<KEY>`, `drop-in`, or the failed step), `LAI-LLM-008` (the model id), `LAI-LLM-014`, `LAI-LLM-015` (the variable). `LAI-LLM-006` and `LAI-AGT-016` are events: raised where they happen and not cleared by `Generate` (an agent restart, or the operator's acknowledgement in the doctor, clears them).

### 4.3 Fit rules (`router.Fit`)

#### 4.3.1 Inputs
From `internal/hardware` (agent.md §4.4) and the profile:

| Symbol | Value |
|---|---|
| `B` | node backend (`cuda` \| `vulkan` \| `cpu`) |
| `G_total` | cuda: VRAM total of the GPU(s) (sum when several); vulkan dedicated: VRAM total; vulkan **unified** (agent.md §4.4.2): GTT total; cpu: 0 |
| `G_others` | GPU memory used by processes that are not children of `localai-llama` (measured, 10 s cache) |
| `M` | `router.memory_margin_mib` from the profile (default 512) |
| `R_total`, `R_avail` | `MemTotal`, `MemAvailable` (MiB) |
| `R_res` | RAM reserve: 2048 MiB, or 4096 MiB on unified-memory nodes |
| `need_v(m)`, `need_r(m)` | `requirements.min_vram_mib`, `requirements.min_ram_mib` |
| `used_v(k)` | for a loaded model `k`: the router's `memory.effective` device total in MiB when reported, else `need_v(k)` |
| `N` | `router.models_max` |

**How it is built** (ROUTER-02, `internal/router`: `fit.go`, `plan.go`, `codes.go`; pure, no I/O). `router.NewEnv(snapshot, backend, profile.Router, W_res)` distils a `hardware.Snapshot` into the symbols above: `G_total` is `Snapshot.FitMemory(B)`, `G_others` is `Snapshot.OthersMiB(B)` (a GPU whose share cannot be measured counts 0), unified is `Snapshot.UnifiedMemory(B)`, `R_total`/`R_avail` are `Snapshot.RAM`. `B` is the node's `llama.backend` or, when empty, the detected one (`cpu` when nothing is known). `router.memory_margin_mib` unset (0) is the default 512. A loaded model's `used_v` falls back to `need_v` when the router's `memory.effective` is absent or not positive. Callers refresh the snapshot before planning (it is at most 10 s old), and `G_others` is never read for static fit.

#### 4.3.2 Static fit (the API's `loadable`)
Evaluated in order; the first failing rule gives `loadable_reason`:
1. `B ∈ requirements.backends`, else `LAI-CAT-005` "This model does not run on <B>".
2. GPU backends: `need_v(m) ≤ G_total − M`, else `LAI-CAT-005` "Needs X GB of graphics memory; this computer has Y GB".
3. Unified memory: also `need_r(m) ≤ R_total − R_res`.
4. CPU backend: `need_r(m) ≤ R_total − R_res`.
5. All backends: `need_r(m) ≤ R_total`.
6. Present (§4.1 step 2), else `LAI-LLM-008`.
`G_others` is deliberately ignored here: a desktop session using 300 MiB must not make a model "never loadable".

**Other engines** (`whisper`, `piper`): the same rules run for every catalog model in `GET /models`, but rule 2 is skipped, because these engines have no graphics-memory requirement (`min_vram_mib` is 0 for them by [catalog.md](catalog.md) §2, and a stray value is ignored). `router.Env.Loadable` and `LoadableAll` (`internal/router/loadable.go`) apply this.

**Messages.** `router.Env.StaticFit` returns `loadable_reason` as `{code, message}` (agent.md §3.8.7) plus the Spanish text (`Reason.Text("es")`; the doctor localization hook of AGENT-11 replaces the two in-package texts when it lands). Sizes are decimal GB with one decimal (`MiB × 1048576 / 1e9`; Spanish uses a decimal comma):

| Rule | English message | Code |
|---|---|---|
| 1 | `This model does not run on <B>.` | `LAI-CAT-005` |
| 2 | `Needs X GB of graphics memory; this computer has Y GB.` (X = `need_v(m)`, Y = `G_total`, not `G_total − M`) | `LAI-CAT-005` |
| 3, 4 | `Needs X GB of memory, and the system keeps Z GB for itself; this computer has Y GB.` (X = `need_r(m)`, Z = `R_res`, Y = `R_total`) | `LAI-CAT-005` |
| 5 | `Needs X GB of memory; this computer has Y GB.` | `LAI-CAT-005` |
| 6 | `The files of this model are missing or not verified on this computer.` | `LAI-LLM-008` |

`LAI-LLM-004` (router down) is never produced by the fit rules: the API layer sets it when it cannot reach the router.

#### 4.3.3 Dynamic fit (at load time)
For a candidate keep-set `K` (models that stay loaded):
- count: `|K| + 1 ≤ N`;
- GPU backends: `need_v(m) + Σ_{k∈K} used_v(k) + G_others + W_res + M ≤ G_total`, where `W_res` is the whisper VRAM reservation ([companion-services.md](companion-services.md) §4.2.3): the resolved whisper model's `requirements.min_vram_mib` when whisper's device resolves to `gpu` **and** `localai-whisper` is not running yet; `0` otherwise (when whisper runs, its memory is already measured in `G_others`, so it is not counted twice);
- unified/CPU: `need_r(m) + Σ_{k∈K} need_r(k) ≤ R_avail + Σ_{e evicted} need_r(e) − R_res`.

A unified-memory node is a Vulkan node, so it must satisfy **both** the GPU rule (against the GTT) and the RAM rule; a dedicated Vulkan card and CUDA are subject to the GPU rule only, a CPU node to the RAM rule only. The RAM rule is deliberately conservative: `Σ_{k∈K} need_r(k)` is counted on top of `R_avail` (mapped weights are reclaimable page cache that `MemAvailable` already counts as free), and an evicted model's `need_r` is credited back. It never over-commits; at worst it evicts one model more than a precise measurement would.

**Eviction planner** (`Env.Plan(m, loaded, unloadOthers) (evict []string, warn *Reason, err error)`): start with `K = loaded set`. While dynamic fit fails: if `unload_others == false` → fail `LAI-LLM-011`; else remove from `K` the least recently used model (by `state.models.last_used`; ties: larger `used_v` first). If `K` is empty and it still fails on `G_others` alone → load anyway with warning `LAI-HW-005` (the router's `--fit` will reduce offload rather than crash), because refusing would leave the node with no model at all.

Details the code fixes (ROUTER-02):
- **Order of the checks.** When `K` is empty there is nothing to unload, so the load-anyway rule applies even if `unload_others` is `false`; `LAI-LLM-011` is only raised while models are still kept. The failing predicate with `K` empty is `G_others + W_res` (the static fit already guaranteed `need_v(m) + M ≤ G_total`), and the warning is `LAI-HW-005` whenever the GPU rule is short.
- **RAM-only shortage.** If, with `K` empty, only the RAM rule (CPU or unified node) fails because other programs hold the memory, the load also goes ahead, with warning `LAI-HW-006`, for the same reason (a node must not be left with no model; the kernel reclaims mapped pages, and `LAI-LLM-027` covers an OOM kill).
- **Result.** `evict` lists the models to unload in unload order (LRU first); it is empty, never nil, when nothing has to go. The planner applies nothing (ROUTER-05 does) and returns `*router.PlanError` (a `Reason` with `LAI-LLM-011`) for a refusal. `warn` is a `Reason` (code, English and Spanish text); the evictions in `evict` still apply when it is set.
- **Tie-breaks.** `last_used` ascending (never used is the oldest), then larger `used_v`, then model id ascending, so the plan does not depend on the order the caller lists the loaded models.
- **No pin.** There is no pinned or protected model: the default model is evicted like any other when it is the least recently used (R8 in §9.3 evicts the default 9B for the VLM). A model keeps its place only by being more recently used, or by `unload_others: false`.
- An entry for `m` itself in the loaded set is ignored (the orchestrator answers "already loaded" in §4.4 step 3 before planning), and a duplicate id counts once. A `models_max` below 1 counts as 1 (lint `LAI-CAT-018` rules it out).

`unload_others: true` (the default) therefore means "unload as many other models as needed, least recently used first", not "unload everything".

### 4.4 Load orchestration (`router.Load(id, wait, unloadOthers)`)

```
          ┌──────────┐ try modelOpsMu    ┌──────────┐ plan ok   ┌──────────┐ all unloaded  ┌─────────┐
request ─►│ checking │──────────────────►│ planning │──────────►│ evicting │──────────────►│ loading │
          └────┬─────┘ busy → 409         └────┬─────┘           └────┬─────┘               └───┬─────┘
               │ 404/422                       │ 409 LLM-011           │ unload timeout          │
               ▼                               ▼                       ▼                         ├── status loaded ──► READY (200)
             error                           error                 rollback                      ├── failed:true / exit ─► cleanup ─► rollback
                                                                                                  └── timeout ─────────► cleanup ─► rollback
  rollback: reload evicted models (most-recent first) ─► RESTORED (500 LAI-LLM-009 / 504 LAI-LLM-010)
                                                      └► nothing loads ─► load default ─► survival list ─► FAILED (500 LAI-LLM-012)
```

Steps:
1. **Check** (no lock): id exists and `engine == llama` (else `404`/`422`); static fit (`422 LAI-CAT-005`/`LAI-LLM-008`); router `/health` 200 (else `502 LAI-LLM-004`). Mode `single` → §4.8.
2. **Lock:** `modelOpsMu.TryLock()`; busy → `409 LAI-AGT-022` with the running `op_id`. (Cloud jobs and `survival_models` wait up to 60 s instead.) Create `op_id`, audit `model.load`.
3. **Snapshot:** `GET /models`. If `id` is `loaded` → release, `200 {already_loaded: true}`. If `loading` (started by someone else) → skip to step 6 (wait).
4. **Plan** (§4.3.3) → `evict` list. Record `previous = loaded set` and `state.models.last_load = {id, op_id, result: "in_progress"}` (fsync; used by crash-resume logic in agent.md §4.2.4).
5. **Evict:** emit `model.loading {model: id, unloading: evict}`. For each `e`: `POST /models/unload {model: e}`, then poll `GET /models` every 500 ms until `e` is `unloaded` (max 30 s). Timeout → treat as failure (go to rollback with nothing new loaded). Emit `model.unloaded {model: e, reason: "evicted"}`.
6. **Load:** `POST /models/load {model: id}` (non-2xx → failure). Poll `GET /models` every 1 s:
   - `status.value == "loaded"` → success;
   - `status.value == "unloaded"` with `failed: true` (or the child exited) → failure (`exit_code` into `details`);
   - deadline `T = llama.load_timeout_seconds` (default 300 s; ×2 when the weights are on an ark drive) → failure (timeout).
   While waiting, `/models/sse` progress (`progress.value`) is forwarded as `model.loading {progress}` at most once per second.
   With `wait: false`, steps 5–8 run in a goroutine after answering `202`.
7. **Success:** `last_used[id] = now`; `state.models.desired_loaded = loaded set` (order = most recent first); `last_load.result = ok, load_ms`; emit `model.loaded`; trigger state push; release lock; `200`.
8. **Failure → cleanup → rollback:**
   1. `POST /models/unload {model: id}` (ignore errors) and wait ≤ 30 s.
   2. Restore every model in `evict` (most recently used first) with the same procedure as step 6 (each its own timeout). Models never evicted are still loaded and are not touched.
   3. If after that **no LLM is loaded** and the effective default ≠ `id` → load the default. In survival mode, if that fails too, walk the profile's `survival.models` list.
   4. Result: something restored → `500 LAI-LLM-009` (failed) or `504 LAI-LLM-010` (timeout) with `details.rolled_back: true, restored: [...]`; nothing loaded at all → `500 LAI-LLM-012` (critical alert).
   5. `last_load.result = failed|timeout`, emit `model.failed`, release lock.

**Never** loop: a rollback load that fails is not rolled back again.

#### 4.4.1 The orchestrator (`internal/router`, ROUTER-05)

`router.Orchestrator` is the one path that loads and unloads models. Its methods are what the HTTP routes (below), the Portal and the cloud call: `Load(ctx, id, wait, unloadOthers, actor)` and `LoadWith(ctx, LoadRequest)`, `Unload(ctx, id, force, actor)` and `UnloadWith`, `SetDefault(ctx, id, actor)`, `LoadSurvivalSet(ctx, skip)` (the `modes.ModelLoader` of the mode engine), `LoadHeld(ctx, id)` (the `ModelLoader` the generator calls while it holds the lock), `Shutdown`, `Wait` and `Counters`. It is built from the router client, the state store, an `Inputs` function (the facts the generator is also given: catalog, profile, `node.yaml`, roots, a fresh `Env`, the mode), the lock, the event bus, the audit log, an alert sink, `Watcher.Suppress`, the watcher's `LatestProgress`, a llama restarter and a generator (for `SetDefault`).

**The lock** is `router.OpLock` (`modelOpsMu`). `TryAcquire` is the non-blocking form (busy is a `*BusyError` naming the holder's `op_id`, which `OpError.Details["op_id"]` carries into the 409); `AcquireWait(ctx, kind, wait)` waits at most `wait` (cloud jobs and `survival_models` pass `DefaultLockWait`, 60 s); `Acquire(ctx)` is the generator's `OpsLocker` and waits until `ctx` ends. Every holder gets an op id when it takes the lock, so a refused caller can always name the one in the way. It is the same lock as the generator's reload, key rotation and the llama restart: build one `OpLock` and hand it to each.

**Errors.** Every refusal and failure is an `*OpError` with `Code`, `Status` (the HTTP status) and `Details`; the mapping is the table of agent.md section 3.8.8 to 3.8.10 and is pinned by `errors_test.go`: `LAI-AGT-021` 404, `LAI-AGT-022` 409, `LAI-AGT-023` 409, `LAI-CAT-005` and `LAI-LLM-008` 422, `LAI-LLM-011` 409, `LAI-LLM-004` and `LAI-LLM-005` 502, `LAI-LLM-009` 500, `LAI-LLM-010` 504, `LAI-LLM-012` 500, `LAI-LLM-007` 500. A caller that cancels its own context gets that error, and `ErrInterrupted` means the agent shut down.

**The routes** (`internal/api/models_ops.go`, `api.RegisterModelOps(reg, api.ModelOpsDeps{Orchestrator: router.NewHTTPOps(orch), LoadTimeout, ModelsMax})`): `POST /models/{id}/load` (op or portal; deadline `load_timeout x (models_max + 2) + 30 s`), `POST /models/{id}/unload` (op, 90 s) and `PUT /models/default` (op, 5 s). The handlers decode (`wait` and `unload_others` default to true, an empty body is fine, `force` for unload, `id` required for the default) and write the typed results; they call the orchestrator through the `api.ModelOps` interface, which `router.HTTPOps` implements (the router package imports the api package, so the interface and its request and result types live in the api package). `HTTPOps` carries the request id into the audit line (`router.WithReqID`) and turns an `*OpError` into the `*api.Error` of the answer: same code, status and details; a message built from the situation (why a model does not fit, why there is no room) is kept in the language of the request, every other message and fix comes from the doctor table. A failed load, a timed out load and `LAI-LLM-012` also set `X-LocalAI-Op-Id`. A **Portal** session may only start a load: its body is ignored and replaced by `wait: false, unload_others: true` (the planner then evicts only what the fit rules require, which is what survival-portal.md section 3.3 asks for as `unload_others = !CanKeepOthers`), and a model that is not loadable is still refused with 422 by the orchestrator. The responses add three optional fields to the bodies of agent.md section 3.8.8 and 3.8.9: `warning {code, message}` on a load that went ahead with `LAI-HW-005` or `LAI-HW-006`, and `restarted` and `restored` on an unload that had to restart llama.

What the code fixes where the steps above are silent:

- **Check.** A model that is not `engine: llama` is `422 LAI-CAT-005`. A model that fits and is present but that the router does not list (its preset is missing) is `500 LAI-LLM-007`, not a load attempt. An `Env.Plan` warning (`LAI-HW-005`, `LAI-HW-006`) is returned as `LoadResult.Warning` and logged; the load goes ahead.
- **Already loaded** also sets `last_used[id] = now`: asking for a model is using it, and it orders the next eviction.
- **The operation outlives its caller.** From the moment the lock is held, steps 5 to 8 run on a context the caller cannot cancel, because stopping after an eviction would leave the node worse off. A caller that gives up (`ctx` cancelled) gets the context error and the operation completes by itself; `wait: false` is the same path with the answer given earlier. Only `Shutdown` stops it.
- **Failure detection.** Each poll of step 6 reads the model's status. `loaded` or `sleeping` is success. `loading` is progress. `unloaded` with `failed: true` is a failure with its `exit_code`; `unloaded` after `loading` was seen means the child exited (a router restart, an OOM kill) and is a failure without an exit code; `unloaded` that was never seen loading is given 3 polls (the router may not have registered the start yet) and then fails. A router that does not answer for 20 s fails the load (`details.cause: "router_down"`); shorter gaps (a llama restart) are tolerated. A model that is no longer in the list fails (`not_listed`). `details.cause` is one of `rejected` (the router refused `POST /models/load`), `failed`, `timeout`, `unload_timeout`, `router_down`, `not_listed`.
- **An eviction that does not finish** (step 5, 30 s) is `500 LAI-LLM-009` with `details.cause: "unload_timeout"` and `details.unloading` naming the model. Nothing new was loaded, the models stopped before it are restored, and the one that would not stop is still loaded, so the answer says `rolled_back: true`. It does not restart llama (only an explicit unload does, section 4.5).
- **Rollback candidates** are tried once each: the evicted models (most recently used first), then, only if nothing is loaded, the effective default (computed from the router's preset ids, section 4.6) and, in survival mode only, the profile's `survival.models`. A model already tried in this rollback, including the one that failed, is skipped, so every load of the rollback is sent at most once. A rollback load that fails or times out is stopped again so it does not hold memory the next candidate needs. `model.unloaded {reason: "rollback"}` is published when the failed model had to be stopped, `model.loaded` for each model restored.
- **The final answer follows what is loaded at the end.** Some model loaded: `500 LAI-LLM-009` or `504 LAI-LLM-010` with `rolled_back: true` and `restored: [...]` (empty when nothing had to be restored). Nothing loaded: `500 LAI-LLM-012`, `rolled_back: false`, the alert is raised, and `state.models.desired_loaded` is left as it was so the boot reconcile retries it; this also holds when the node had no model before the request. After any other failure `desired_loaded` is set to what is loaded now. A later successful load clears `LAI-LLM-012`.
- **State.** `last_load` is written with `MutateSync` before the first eviction (`in_progress`, `at` = start) and at the end (`at` = end; `load_ms` measures step 6 only, not evictions). A state file that cannot be written is logged and the operation goes on: a read-only disk must not keep a node from loading a model. `interrupted` is written only by a clean shutdown; after a kill the file still says `in_progress`, which is what the mode engine reads to skip a model that may have crashed the box (agent.md section 4.2.4). A graceful stop is not suspicious, so `interrupted` is not skipped.
- **Shutdown** (`Orchestrator.Shutdown`, agent.md section 4.12 step 6) stops the polling loops. The router calls that were sent are not undone and no rollback runs; `last_load.result` becomes `interrupted`, no `model.failed` is published, the lock and the watcher suppression are released. After `Shutdown` a new `Load` or `Unload` answers `ErrInterrupted` at once, touching nothing.
- **Audit and events.** One `model.load` line per call, written when the operation ends (a `wait: false` call writes it from the background goroutine), with `result` and the doctor `code` of a failure; a refused call (busy, 404, 422) is audited as a failure without an `op_id` of its own. Events carry the `op_id`; `model.loading` is published once with the evict list and again at most once per second with `progress` (from the watcher's `LatestProgress`).
- **Counters** (`Counters()`): loads ok and failed, rollbacks, and per model the count, last and mean `load_ms`; they feed `/status?counters=1` and the heartbeat. Logs are `component=router` with `op_id`, `model`, `phase`, `duration_ms`, `code`.
- **Single mode** (section 4.8) is ROUTER-07: `Load` will dispatch to it when `llama.mode` is `single`; until then the orchestrator is the router-mode path only.

**`LoadSurvivalSet(ctx, skip)`** (agent.md section 4.2.1, step `survival_models`): reads the profile's `survival.models` and `models_max`, counts the survival models already loaded, then loads the others in order (each with `LockWait: 60 s`, `unload_others: true`, the load timeout, the rollback of this section) until `models_max` of them are loaded. Ids in `skip` are not tried. Each model that fails gives the warning `LAI-LLM-020` and the next is tried; when no model is loaded at the end `LAI-LLM-021` is added. An error means it could not even try (no survival list, the router does not answer, shutdown).

### 4.5 Unload (`router.Unload(id)`)
Lock as in §4.4 step 2. `POST /models/unload`, poll until `unloaded` (≤ 30 s). If the router still reports it running after 60 s → `systemctl restart localai-llama`, then restore the remaining `desired_loaded` set and raise `LAI-LLM-031`. On success: remove `id` from `desired_loaded`, emit `model.unloaded {reason: "request"}`. The default model may be unloaded; `state.models.default` is unchanged.

#### 4.5.1 What the code does (ROUTER-05)
- **Two waits.** An eviction inside a load waits 30 s (a failure rolls back); an explicit unload waits **60 s** before the router counts as hung. The 30 s of the paragraph above is the normal case, the 60 s the point of no return: the router gives a child 10 s and then kills it, so both are far beyond a normal stop.
- **Checks** (before the lock): the id is in the catalog or listed by the router (`404 LAI-AGT-021`), is a llama model (`422 LAI-CAT-005`), and the router answers (`502`). A catalog model the router does not list, or that is not running, answers `200 {already_unloaded: true}`. In survival mode, unloading the only loaded model is `409 LAI-AGT-023` unless `force`.
- **The hang path:** `systemctl restart localai-llama` (the `LlamaRestarter` port), wait for `/health` (at most 120 s), load again the other models of `desired_loaded` in order while `models_max` allows, then, if nothing is loaded, the effective default and (survival mode) the survival list, and raise `LAI-LLM-031`. The unload counts as done (`200`, `restarted: true`, `restored: [...]`) and `desired_loaded` loses `id`. If nothing could be loaded: `500 LAI-LLM-012`. If the restart itself fails: `502 LAI-LLM-004` with `details.cause: "restart_failed"`. Without a restarter configured: `504 LAI-LLM-031`.
- The caller cannot cancel the operation once the lock is held, as for a load (section 4.4.1).

### 4.6 Default model and boot
`Orchestrator.SetDefault(ctx, id, actor)` (agent.md section 3.8.10): the model must be in the catalog, `engine: llama`, present and statically fit (`404`, `422 LAI-CAT-005`, `422 LAI-LLM-008`). It writes `state.models.default`, calls `Generator.Generate` with that default (the `load-on-startup` flag moves; the reload-safety rule of section 4.2 step 8 decides whether the router is told, and a default change alone never reloads), and publishes `model.default_changed {model, previous}` when the default moved. `previous` is the default in force before: the recorded one, else the profile's. It never loads or unloads a model. It does not take `modelOpsMu` itself, because the generator takes it when a reload would unload something; a second `SetDefault` waits for the first. If the generator cannot write the file the recorded default is put back and the answer is `500 LAI-LLM-007`; if the file is written but the router could not be told (a busy lock, the router down) the answer is still `200` and the next generation applies it.

- **Effective default** = `state.models.default` if set and it has a preset; else the profile's `default_model` if it has a preset; else (survival mode) the profile's `survival.default_model`; else none (`LAI-LLM-014`).
- The effective default's section carries `load-on-startup = true` (§3.5.1). So **the router loads the default model by itself at boot**, before the agent is even running. If the default is not loadable at all, no section has the flag.
- After the agent starts (agent.md §4.1 step 14), it reconciles: wait for router `/health` (≤ 120 s), then for the default's status to leave `loading` (≤ load timeout). If the default is not `loaded`, load it via §4.4 (failure → `LAI-LLM-013`). Then load the rest of `desired_loaded` (most recent first) while `models_max` and dynamic fit allow, with `unload_others: false` (boot never evicts). In survival mode the survival set replaces `desired_loaded` if no LLM is loaded.
- `models_max ≥ 1` is guaranteed by catalog lint (`LAI-CAT-018`, [catalog.md](catalog.md) §7), so the router never rejects startup for too many `load-on-startup` models.

#### 4.6.1 What the code does (ROUTER-06)
`internal/router/boot.go` has the two boot steps of agent.md §4.1:

- **`Reconciler.Reconcile(ctx)`** (step 12; `NewReconciler(ReconcileOptions{Units, Models, Inputs, Router, Unit})`). In one 30 s budget (`DefaultReconcileBudget`): (1) `UnitGenerator.Generate` renders the unit and, when the file changed, runs `daemon-reload` (once; a drop-in change makes the preset generator run its own, harmless, second one); (2) `Generator.Generate` renders `models.ini` and the drop-in and, when the file changed and the router answers, tells it to re-read the file under the reload-safety rule (`GET /models?reload=1`; a running model whose preset did not change stays loaded); (3) when `/health` does not answer, the unit is enabled and it is not already running (`active`, `activating` or `reloading`), the unit is started. Each step runs even when an earlier one failed, and the returned error joins what failed (`ErrReconcileBudget` when the 30 s ran out); the caller opens the mutating-route gate either way. In `single` mode (`UnitInputs.Mode`) `models.ini` is left alone (section 4.8). Reconcile never restarts a running llama: a unit or environment change that needs one raises `LAI-AGT-016` and waits. The systemd seam is `router.LlamaUnit{State, Start}` (state: `Running`, `Enabled`); the wiring adapts `services.Manager` with `services.UnitLlama`.
- **`Orchestrator.RestoreModels(ctx)`** (step 14, background). It waits for `/health` (at most `Timing.RestartWait`, 120 s) and then, in this order:
  1. computes the effective default from the router's own preset list (`EffectiveDefault`; none raises `LAI-LLM-014`, a default clears it);
  2. if the default is `loading` (load-on-startup), waits for it to leave that state, at most its load timeout (`loadTimeout`: doubled on an ark drive). A default that is `loaded` counts and no load is sent. A default that is still loading when the timeout ends is `LAI-LLM-013` with `cause: timeout`; it is not loaded a second time, because that would hold `modelOpsMu` for another load timeout;
  3. in survival mode with no model loaded, `LoadSurvivalSet` runs and the restore ends (the survival set replaces the desired set). If the survival set cannot be applied at all (no list, a router that stops answering) the normal path below runs;
  4. a default that is not loaded is loaded through `LoadWith` (`wait: true`, `unload_others: false`, actor system, `LockWait: DefaultLockWait`, so an operator's load in progress is waited for, not refused). Failure (not loadable, a failed or rejected load, a timeout) raises `LAI-LLM-013` and the restore goes on. **No room is not a failure:** when another model is loaded and the default does not fit beside it (an agent restart while the operator's own choice is loaded), boot never evicts, nothing is alarmed and the default is reported as `no_room`;
  5. the rest of `state.models.desired_loaded`, most recently used first (the stored order breaks ties), each through `LoadWith` with `unload_others: false`, until `models_max` models are running; the ones that do not fit, or cannot be loaded (not in the catalog, not a llama model, no preset, failed), are in `RestoreResult.Skipped` with a doctor code and a reason. A model that is `loading` already is waited for, never loaded twice (agent.md §5, "agent restarts while llama is loading").

  The result (`RestoreResult`: `Default`, `DefaultState`, `Loaded`, `Started`, `Skipped`, `Survival`, `Warnings`) is also the log line `boot restore done`. The error is nil whenever the restore ran; it is `LAI-LLM-001` (`details.cause: health_timeout`) when the router never answered, and `ErrInterrupted` or the caller's error otherwise. A successful default clears `LAI-LLM-013`.

  **`desired_loaded` during and after.** A load rewrites it to what is loaded, so a crash after the default came up would forget the models still waiting; `RestoreModels` therefore keeps the waiting ones in the list while it runs (loaded first, then the pending) and the list ends as what is loaded, as after any load. If nothing could be loaded it is put back as it was, so the next boot retries.

### 4.7 Autoload is disabled (`--no-models-autoload`)
The unit always passes `--no-models-autoload`; the profile field `router.autoload` exists only so that this is explicit, and catalog lint requires it to be `false` ([catalog.md](catalog.md) §4, §7).

By default the router starts any model named in a request. We turn that off, because:
1. a stray request (a client with a stale model name, a WebUI dropdown click, a gateway retry) could evict the survival model or OOM an 8 GB laptop without the fit rules running;
2. loads must be serialized, audited and rolled back by the agent (§4.4), which only happens on the agent's path;
3. `models_max` LRU eviction inside the router would silently unload the model an operator just chose.
Consequence: a request for an unloaded model gets an error from the router. Clients see a clear message; the gateway only routes to models reported `loaded` (§4.12). The WebUI dropdown still lists every preset; selecting an unloaded one shows the router's error. Operators load models through the agent (`aictl load`, desktop, Portal, cloud). `--sleep-idle-seconds` is also **not** used (a sleeping default model would make the first request after idle slow and confuse the Portal); see §11.

### 4.8 `single` fallback mode
- Selected by `node.yaml: llama.mode: single`. The agent generates §3.4 instead of §3.2 and does not write `models.ini` (it leaves the last one in place).
- Status: `GET /v1/models` (lists the one model and its aliases) replaces router `GET /models`; the model is `loaded` when `/health` is 200 and the id is listed.
- Load X: lock; if X is current → `already_loaded`; else back up the unit, render the unit for X, `daemon-reload`, `systemctl restart`, wait `/health` 200 + X listed (deadline = load timeout). Failure → restore the previous unit, restart, wait, `500 LAI-LLM-009` (rolled back) or `LAI-LLM-012`. Success → `state.models.default = X` (in single mode the loaded model **is** the default).
- Unload in single mode → `409 LAI-AGT-023` ("single mode always has exactly one model"), unless `force`, which stops the unit.
- Switching `router ↔ single` = edit `node.yaml`; the agent regenerates the unit (§3.4.1), `daemon-reload`, restarts llama and restores the default. `LAI-LLM-023` (info) while single mode is active. The unit generator itself only raises `LAI-AGT-016` for the changed command line (`llama.mode` is a restart-on-demand setting, agent.md §3.4); the restart belongs to the single-mode orchestration (ROUTER-07).

### 4.9 Migration from `llama-qwen.service`

Today every node runs a hand-written `/etc/systemd/system/llama-qwen.service` (user `marinoscar`, binary under `~/llama.cpp/build-*`, model under `~/models`, key at `/etc/llama-qwen/api-key`, port 8080, Tailscale Serve to 8080). The migration replaces it with `localai-llama.service` **in place**: same port, same key, same Tailscale Serve, same public URL, and the old model name still works. Clients (Open WebUI via the VPS vhost, OpenCode on the node, the gateway) need **no change**.

Entry point: `sudo aiagent migrate llama-qwen [--dry-run]` (agent.md §3.1, flags and behaviour: §4.9.5), called by `install-node.sh` on nodes that have `llama-qwen.service` ([installer.md](installer.md) §4.3 P8). Every step is idempotent and its progress is recorded in `/var/lib/localai/migration/llama-qwen/progress.json` (`{step, at, t0?}`); re-running continues from the recorded step. Downtime of inference is only between M6 and M7 (typically 10–30 s: the model load time).

**Single writer rule:** a non-dry run first stops `localai-agent.service` (if running) so that `node.yaml`, `state.json` and `models.ini` have one writer, and starts it again after M10 or after a rollback (the agent then reconciles normally, agent.md §4.1). Inference is not affected: `llama-qwen.service` keeps serving until M6. At the end the migration writes `state.migration.llama_qwen = {state, step, at}` and `state.models.default` itself.

#### 4.9.1 Preconditions
- The agent is installed and running (`localai` user and groups exist, `/srv/localai` exists, catalog loaded).
- The catalog contains the node's current model(s) with the **exact sha256** of the files on disk (catalog.md §2.1 says the entries are recorded from the nodes).
- Enough free space on `/srv/localai`'s filesystem **only** if `~/models` is on a different filesystem (else files are renamed, not copied).

#### 4.9.5 What the code does (ROUTER-09)
`internal/router/migrate` is the engine (`Preflight`, `Prepare`, `Run`, `Rollback`, `Pending`), `internal/router/migrate/host` wires it to the real machine, and `cmd/aiagent/migrate.go` is the command. The engine imports no `os/exec`, no HTTP and no systemd: the filesystem, systemd (`services.Manager` behind `services.NewGuard`), programs (`execx.Runner`), the router (`Probe`), the build manager, node.yaml, state.json, the preset and unit generators and the audit log are seams, so the tests run the whole migration on in-memory fakes with a manual clock (no test sleeps).

- **Command.** `aiagent migrate [llama-qwen] [--dry-run] [--rollback] [--accept-catalog-flags] [--restore-files] [--yes]`, root only (`LAI-CLI-006`). With no name it runs the pending migration and exits 0 with "Nothing to migrate." when there is none (pending: `llama-qwen.service` installed and not masked, or an interrupted migration or rollback). It takes the same lock as every `aictl` command that changes node files. A run that changes the node asks for `yes` at a terminal; without a terminal it refuses with `LAI-CLI-007` (exit 2) unless `--yes` is given, so the installer calls `aiagent migrate --yes` ([installer.md](installer.md) §4.3 P8). Exit 0: done, nothing to do, a dry run that would pass; 1: refused or failed (code, title and fix on stderr); 2: usage or no confirmation. The admin PIN is not asked: this is a root shell on the machine, as for `aictl pin set`.
- **Dry run.** M0 reads and hashes and prints the plan: one line per step M0 to M10, the flag differences, the warnings and every problem with its code and fix. It writes nothing, not even `plan.json` or `serve-before.json` (the real run writes both first thing), and exits 0 only when there is no problem. `--rollback --dry-run` prints R1 to R6.
- **Journal.** `progress.json` is `{step, at, t0?}` plus `t_loaded`, `rollback` (`R0` to `R6`), `cause`, `restore_files` and `agent_stopped`. `step` is the last step that completed; every step is idempotent, so one killed between its effect and its record simply runs again. A re-run reads the file: a migration in progress continues from the next step, a finished one (`M10`) only repairs the key link (`LAI-SEC-015`), a rollback in progress finishes, a finished rollback (`R6`) allows a new migration. `state.migration.llama_qwen` follows it: `in_progress`, `done` (from M9), `rolling_back`, `rolled_back`. `agent_stopped` is recorded before the agent is stopped, so a killed run's successor starts it again.
- **Killed between M6 and M7.** The journal records `t0` before the old service is stopped. A resume that finds `t0` set, the step before M6 and neither unit active starts `llama-qwen.service` again and waits for it before going on; a resume at M6 or later goes forward (starts the new unit).
- **Automatic rollback** runs for a failure of **M6, M7 or M8** (the old service is stopped or about to be), under a context that ignores Ctrl-C, and ends with `LAI-LLM-029` and `rolled_back: true`. A failure of M1 to M5 leaves the old service serving and the progress where it was; a failure of M9 or M10 keeps the verified new service and a re-run finishes.
- **M0 details.** A model file is matched by the sha256 of its content against every `files[].sha256` of the catalog; `-md` and `--mmproj` must match files of the same model. The other files of that catalog entry (the shards of a split model) are looked for next to the named ones and hashed too, because the effective set needs every file of the entry (`LAI-LLM-017`, cause `file_missing`). Flags the diff does not name (`--jinja`, `-t 8`, ...) count as differences unless the catalog's `extra_args` has them. `-ngl all` and `-ngl 99` (or more) are the same. The unit must read its key from `/etc/llama-qwen/api-key` (an inline `--api-key` or another file stops the migration). Only `GGML_*` environment variables are carried to `llama.extra_env`; any other `Environment=` and any `EnvironmentFile=` is listed as a warning. `tailscale serve status --json` is stored in a canonical form; a node without Tailscale compares "unavailable" with "unavailable". The public URL (M8e) is asked only when `state.connectivity` is `full` or `internet` and `node.public_host` is set, and it fails the migration only if it answered 200 in M0.
- **M1.** The build never activates: the build manager runs with `NoActivate` and the migration switches `current` itself (an atomic link) and records `state.llama.build`, so `localai-llama` is never restarted while the old service holds the port. A finished build of the commit that an earlier, killed run left is reused. `--version` must show the commit and `--list-devices` a `CUDA` device, or a Vulkan device that is not `llvmpipe`. The source is the legacy checkout (`git archive`), then the kit mirror; never the network.
- **M3.** `<new>` is `/srv/localai/models/<id>/<name>` with `<name>` the catalog's file name (it equals the old basename for every model of the catalog; the effective set looks for exactly that name in `MANIFEST.json`). `MANIFEST.json` is written last: `source.type` is `adopted` (with the catalog's `repo` and `revision`), `version` the first 12 characters of the revision (so sync sees the item as current), `trust` `pinned`.
- **M9.** The old unit file and the files of its drop-in directory are copied to `llama-qwen.service` and `llama-qwen.service.d/` in the migration directory (never overwritten once the unit is gone), then removed from `/etc/systemd/system`; `disable`, `mask` and `daemon-reload` follow. The key link and the links that replace the files copied across filesystems are each made as a link under a temporary name and renamed over the path, so the path is never missing.
- **Rollback.** R2 also puts the drop-ins back. R3 restores a regular file whenever the old key path is a link or gone, from the current key. R4 with `--restore-files` renames same-filesystem files back, gives them to the old unit's user and group, and removes the manifest it wrote; a file that was copied across filesystems stays and its link keeps working (said in the output). R5 waits up to 120 s for `/health`, 200 with the key and 401 without.
- **The agent.** `localai-agent.service` is stopped and started through the systemctl Manager without the daemon's allowlist (which allows nothing but a restart of the agent's own unit); the migration is not the daemon.
- **Doctor.** `llm.legacy_service` (`LAI-LLM-016`), `llm.migration` (`LAI-LLM-029`: state `in_progress` or `rolling_back` while the agent runs) and `sec.legacy_key_path` (`LAI-SEC-015`: state `done` and the old key path is not a link to `/etc/localai/api-key`), registered by the daemon (`migrate.RegisterChecks`).
- **Codes.** `LAI-LLM-017` for every stop of M0 and M5, `LAI-SEC-010` for a key that is not 64 lowercase hex digits, `LAI-LLM-018` or `LAI-LLM-019` from the build, `LAI-LLM-029` for everything after the first change. None is new. The key is never printed, logged, audited or passed on a command line; only its fingerprint (`ab12…9f3c`) is, and the tests scan every output, log, audit line and file of the migration directory for it.

`-G Ninja` is always used (`ninja-build` is a build prerequisite on every backend, and is in the kit debs, [rebuild-kit.md](rebuild-kit.md) §4.1.4). `-DLLAMA_BUILD_COMMIT=<full sha>` is always passed: the source tree is extracted from a tarball or `git archive` and has no `.git`, so without it llama.cpp reports `commit unknown` in `llama-server --version` and the smoke test of §4.10.3 step 3 would refuse every build (found by the real build of the `llama-build` CI workflow; it also makes the version line name the commit of the pin rather than of whatever checkout was at hand).

|---|---|---|

#### 4.10.4 What the code does (ROUTER-08)
`internal/router/build` is the engine of §4.10; `aictl rebuild-llama` (AICTL-09) and `aiagent migrate` (ROUTER-09) call it in-process, as root, never from the daemon. AICTL-09 implements the seams of the command side in `internal/cli/cmd_rebuild_llama_wire.go` (`build.Agent` over `POST /services/llama/restart`, `build.Probe` over the router and the agent, `build.StateRecorder` over `state.json`; [aictl.md](aictl.md) §4.23). It imports neither `internal/api` nor `internal/cli`: the agent, the router, the state file, the audit log and every program are seams, so the tests run on a temporary directory with a fake `execx.Runner` and a manual clock.

- **Entry points.** `Manager.Resolve(ctx, Request) (Inputs, error)` resolves commit, backend, CUDA arch and jobs and changes nothing (the confirmation line "Building llama.cpp f3586e66b for cuda (sm 75), 5 parallel jobs"); `Manager.Preflight(backend)` resolves the prerequisite programs; `Manager.Build(ctx, Request) (Result, error)` runs §4.10.1 to §4.10.3 and the retention. `Request` carries the engine's flags of aictl.md §4.23 (`Commit`, `Backend`, `CudaArch`, `SourceDir`, `Jobs`, `NoActivate`, `Keep`, and KIT-04's `FromKit`, `DryRun`, `Prebuilt`; `--yes`, `--json` and the output are the caller's) plus `Offline`, `Sources`, `Actor` and a `Progress` callback. `Jobs` is capped like the default: `min(--jobs, nproc, floor(MemAvailable_GiB / 2))`, at least 1. The compile runs as the `localai` user and the new build's smoke test also writes a few words with the smallest verified model (rebuild-kit.md §4.3 and §4.3.3); `Options.CompileUser` and `Options.SmokeModel` are the seams. `Result` is `{build_id, switched, previous_build, build_json}` (the `--json` of aictl.md §4.23); the Go struct also carries `DefaultModel`, `Warnings` and `Removed` for the human output. Empty `Commit`, `Backend` and `CudaArch` take `node.yaml`'s values.
- **Errors** are `*build.Error{Code, Stage, Message, Details}`; a cancelled context returns `ctx.Err()` after removing the half-built directory (current untouched). `LAI-LLM-018`: a missing prerequisite (`details.missing`, `details.packages`; the message carries the `sudo apt install` command), less than 2 GiB free on `/opt`, a failed configure or build with its exit status or timeout, a missing program after the build, a source that has the commit but cannot deliver it, another build holding the lock. `details.log_tail` is the last 200 lines of `build.log`, `details.log_path` its path, and `details.hint_packages` names the apt package a known log line points at. `LAI-HW-019`: no CUDA architecture. `LAI-KIT-002`: offline and no source has the commit. `LAI-KIT-001`: a kit tarball or prebuilt build that does not match its recorded checksum. `LAI-KIT-010` to `LAI-KIT-014`: the failed checks of the offline preflight of a `FromKit` or `DryRun` build. `LAI-LLM-019`: the smoke test or the relocatable check failed, or the activation failed (`details.cause`: `symlink`, `restart_failed`, `health_timeout`, `default_lookup`, `model_failed`, `load_failed`, `load_timeout`, `completion_timeout`, `completion_failed`; `details.rolled_back`). `LAI-AGT-022` (the CLI's exit 6): the agent stayed busy for 60 s.
- **Inputs.** The build id is `<first 9 characters of the full sha>-<backend>`. Several GPUs give the sorted, de-duplicated list (`7.5`, `8.9` → `75;89`; `10.0` sorts after `7.5`). `Jobs(nproc, MemAvailable)` is the formula of §4.10.2. The configure step has its own 30 min timeout; the build step has the 3 h. Programs run with `PATH` = the fixed path and `LC_ALL=C`. Each command is appended to `build.log` with its output and exit status.
- **Source** is a chain of `Source` values tried after the already-extracted `src/<commit>/` (a short commit finds its tree by prefix): `GitArchiveSource{Repo}` (`git archive`, for the legacy checkout and, with `<root>/kit/git/llama.cpp.git`, the kit mirror; every git call carries `-c safe.directory=<repo>` because a root process reads a repository another user owns), `DirSource{Dir}` (`--source`: a git checkout is read with `git archive <commit>`, a plain tree is copied without `.git` and needs a full sha; it replaces the tree already extracted), `GitCloneSource{URL}` (online only; the `.git` directory is removed after the checkout so every source yields the same plain tree). A source that does not have the commit returns `ErrNotAvailable` and the chain goes on; a source that has it and fails is remembered, and when nothing else delivers it the result is `LAI-LLM-018`, not `LAI-KIT-002`. Trees are extracted into `src/<commit>.tmp` and renamed, so a tree at its final path is whole (a directory without `CMakeLists.txt` is replaced). Tar extraction (`ExtractArchive`) refuses `..`, absolute names, hard links and special files, symlinks that leave the tree or are not in cleaned form, entries whose parent is a symlink and files that would replace a symlink. `Request.Sources` replaces the chain for one build; `Request.FromKit` replaces it with `KitSources` (the verified kit tarball on any root, then the kit mirrors; KIT-04, [rebuild-kit.md](rebuild-kit.md) §4.3 "What the code does"), and a source that has the commit but whose copy fails its checksum is `ErrSourceDamaged`, which the chain skips and which ends the build with `LAI-KIT-001` when nothing else delivers the commit. Using a tree touches its directory: that is how "the last 2 commits" is decided.
- **Failures keep evidence.** After the build directory exists, any failure renames `<id>.tmp` to `<id>.tmp.failed` (the build tree `B` is deleted, `build.log` stays). A failed relocatable check (a `RUNPATH`/`RPATH` into `/home` or into `builds/*.tmp`, or a program that is not an ELF file) is `LAI-LLM-019` like a failed smoke test. Rebuilding the build that `current` points at without activation is refused (it would replace the running build silently); with activation the old directory moves aside to `<id>.old-<ts>` and is the build the rollback returns to.
- **Switch.** `current` moves with a new symlink `current.tmp` renamed over it. With the agent up, `Agent.RestartLlama` (`POST /services/llama/restart`) restarts and restores the models; a busy agent (`409 LAI-AGT-022`) is retried every 5 s for 60 s, after which the link is put back (the unit was never restarted) and the build ends with `LAI-AGT-022`. With the agent down, or one that stops answering, `systemctl restart localai-llama.service` runs, and `StateRecorder` (when given) records `state.llama.build` afterwards; with the agent up the agent's own restart path records it (§4.11.1) and the engine never writes the state file. The post-switch check is `Probe`: `/health` within 60 s of the restart; then the default model is `loaded` (`LoadModel` when it is neither loaded nor loading; with no agent the router's own `load-on-startup` is awaited), then a 16-token completion; everything within 180 s of the restart (a poll every 2 s). With no default model only `/health` is checked, with a warning. Any failure puts the previous link back and restarts again the same way, even when the caller gave up meanwhile; with no previous build there is nothing to put back and `details.rolled_back` is `false`. `llama.build.switch` is audited once per attempt (`result` ok or fail, `code`, target `build`, `previous`, `backend`, and on failure `cause` and `rolled_back`).
- **Retention** runs after a good build only. `--keep n` (default 2) is the number of builds kept besides `current`: the previous build always, then the newest others (by `built_at`), so the default keeps exactly `current`, the previous build and the newest other. After a switch the previous build is the one `current` pointed at before; without a switch it is `state.llama.previous_build` (`Options.PreviousBuild`). A `<id>.old-<ts>` directory counts as a build; leftovers (`*.tmp`, `*.tmp.failed`) are deleted by a later good build, and directories without a `BUILD.json` are not touched. Source trees keep the last 2 by last use plus the one just built. A deletion that fails is a warning in `Result.Warnings`.

### 4.11 Key rotation and llama restarts
`POST /key/rotate` (agent.md §3.8.14) and `POST /services/llama/restart` both: take `modelOpsMu`, restart the unit, wait `/health`, then restore `desired_loaded` (default first, then most recent first, `unload_others: false`). The router itself loads the default via `load-on-startup`; the agent only loads the rest.

#### 4.11.1 What the code does (ROUTER-06)
`internal/router/restart.go`:

- **`Orchestrator.RestartAndRestore(ctx, actor)`** is `RestartWith(ctx, RestartRequest{Actor, LockWait, Prepare})` with no lock wait and no `Prepare`; `Prepare(ctx, opID)` runs once the lock is held and before the unit is restarted, and an error from it aborts the restart and is returned as it is (key rotation writes the new key file in it, so a busy lock leaves the old key in place); key rotation, the llama service restart and the build switch call it. It takes `modelOpsMu` without waiting (busy: `409 LAI-AGT-022` with the holder's `op_id`, nothing is touched; the holder kind is `restart`), suppresses the watcher, restarts through `OrchestratorOptions.Restarter` (`LlamaRestarter`), records the installed build, waits for `/health` (`Timing.HealthWait`, 60 s) and restores. Errors: `500 LAI-LLM-001` with `details.cause: restart_failed` (the unit did not restart) or `health_timeout`, both with `details.op_id`; a key rotation that gets one keeps the new key and adds `key_rotated: true` itself (agent.md §3.8.14). As for a load, once the lock is held the operation cannot be cancelled by its caller (only by `Shutdown`): stopping halfway would leave llama down; a caller that gives up gets its own context error.
- **The restore** runs under the lock it already holds (so it does not use `LoadWith`): the effective default first (waited for when the router is loading it, loaded when not), then `desired_loaded` most recently used first. Each model is waited for when it is `loading`, left alone when it is `loaded`, and otherwise loaded when it is a llama model with a preset that fits next to what is loaded with `unload_others: false` (static fit, then `Env.Plan`; no eviction ever). A model that fails or times out is stopped again so it does not hold memory the next one needs. `model.loaded` is published for each model the agent loaded. `state.models.desired_loaded` is not rewritten (a model that had no room is still wanted). In survival mode, when nothing is loaded after that, `survival.models` are tried in order until `models_max` are running. `RestartResult.Restored` lists the models of the restore set that are loaded at the end, default first, **including the ones the router brought back itself**: it is the `restored_models` of the routes.
- A default that does not start raises `LAI-LLM-013` (cleared when it does). When the restore set was not empty and nothing at all is loaded at the end, `LAI-LLM-012` is raised (`cause: restart_restore`) and the call still succeeds with an empty `Restored`: the unit is back, and the route reports what happened instead of failing a restart that worked. A `single`-mode node (`node.yaml llama.mode`) only restarts and waits for `/health`.
- **Build record.** After a successful restart `state.llama.build` is set from `current/BUILD.json` (`FileBuild`, field `build_id`; `OrchestratorOptions.Builds`) and the build it replaces becomes `previous_build`; an unreadable file, or the same id, leaves the record alone.
- **`router.LlamaHook`** (`NewLlamaHook(orchestrator)`) is the `api.LlamaRestarter` of `POST /services/llama/{action}` (agent.md §3.8.22): it takes the lock without waiting (`*api.BusyError` with the holder's op id when busy, and the unit is not touched), runs the route's unit action while holding it, and after a `start` or `restart` does the steps above, returning `Restored`; a `stop` restores nothing. An error of the unit action is returned as it is (the route maps `*services.ActionError`); a router that did not answer afterwards is the `*api.Error` of `500 LAI-LLM-001`. The events and the watcher suppression carry the route's `op_id`.

### 4.13 `aictl bench <model>`
Measures throughput and **VRAM** for the catalog's `min_vram_mib` (catalog.md §2 requires a measured value).
1. Preconditions: model present; operator confirms that loaded models will be unloaded (`--yes` to skip). The bench runs in the `aictl` process and drives the agent's load/unload routes, so it cannot hold `modelOpsMu` across the whole run: it refuses to start while a model operation is running, watches `/events` during the run, and marks the result `"disturbed": true` (and does not print a catalog suggestion) if any other model operation happened meanwhile.
2. Unload all models (record them for restore). Sample baseline GPU memory `U0` (5 samples, 1 s apart, median).
3. **VRAM at real context:** load the model with `POST /api/v1/models/{id}/load` (nothing else is loaded, so no eviction). Send one chat completion (`max_tokens: 64`, prompt ~512 tokens) to force KV and compute buffers. Sample GPU memory every 250 ms during the request (in-process, with the same hardware probes the agent uses — not through `GET /hardware?fresh=1`, whose 1-sample-per-2 s limit, [agent.md](agent.md) §3.8.6, does not apply to the bench); `U1` = peak. `measured_vram_mib = U1 − U0`. Also read `GET /models` `memory.effective` when present (recorded, not used).
4. **Throughput:** unload it (`POST …/unload`); run `current/bin/llama-bench -m <weights> -ngl <n_gpu_layers> -fa <flash_attn> -p 512 -n 128 -r 3 -o json` (llama-bench does not exercise speculative decoding, so the speed with MTP/draft is taken from the step 3 response `timings` as `server_tg_tps`, with the draft acceptance from the router log). Timeout 15 min.
5. Restore the previously loaded models.
6. Write `/var/lib/localai/bench/<id>-<ts>.json`:
```json
{"model": "qwen3.5-9b-q4km", "node": "ai-n3", "build": "f3586e66b-cuda", "gpu": "NVIDIA GeForce RTX 2070 with Max-Q Design",
 "ctx": 32768, "baseline_vram_mib": 210, "peak_vram_mib": 6791, "measured_vram_mib": 6581,
 "suggested_min_vram_mib": 7240, "pp512_tps": 1450.2, "tg128_tps": 38.4, "server_tg_tps": 41.0, "mtp_acceptance": 0.71,
 "measured_at": "2026-11-02T10:30:00Z"}
```
`suggested_min_vram_mib = ceil(measured × 1.10)`. The command prints a YAML snippet for the catalog PR (`requirements.min_vram_mib: 7240`, a comment with GPU, build and date).
7. CPU-only nodes: VRAM fields are null; `min_ram_mib` is suggested from RSS of the child (`/proc/<pid>/status VmRSS`) peak × 1.10.

#### 4.13.1 The engine (`internal/router/bench`, ROUTER-10)

The measurement engine is the package `internal/router/bench`; `aictl bench` (AICTL-05, [aictl.md](aictl.md) §4.24) calls `bench.New(deps, opts).Run(ctx, id)` after the confirmation and prints the returned `*Result` (`Result.Snippet()` is the YAML of step 6). Nothing in the agent imports it. The package imports neither `internal/api` nor `internal/cli`; the agent is reached through seams that AICTL-05 implements over the HTTP client:

| Seam | Used for |
|---|---|
| `Agent.Models`, `Agent.Model` | `GET /models` (statuses; a model in `loading` makes the run refuse), `GET /models/{id}` (`present`, `verified`, engine, the `preset` text, the router's `memory.effective`) |
| `Agent.Load`, `Agent.Unload` | `POST /models/{id}/load` with `{"wait": true, "unload_others": false}` and `POST /models/{id}/unload` with `{}`. The engine never evicts a model it did not unload itself. A `409 LAI-AGT-022` comes back as `*bench.BusyError` |
| `Agent.Events` | `GET /events?types=model.*`, opened before anything else is looked at |
| `Chatter.Chat` | the one chat completion to the router (the engine never holds the key) |
| `GPUSampler.SampleGPUs` | `hardware.Sampler.SampleGPUs` in-process (step 3, every 250 ms) |
| `Procs` | CPU-only nodes: the cgroup pids of `localai-llama.service` and each pid's `VmRSS` (`bench.NewProcFS`) |

Rules the code adds to the steps above:

- **What is measured.** The model's weights path, `ctx` (`c`), `n-gpu-layers` and `flash-attn` are read from the preset text of `GET /models/{id}`, so the bench runs the model exactly as the router does. A preset without an absolute `model` path or without a positive `c` refuses with `LAI-LLM-025`. Model absent or unverified: `LAI-LLM-008`; unknown id: `LAI-AGT-021`; an engine other than `llama`: `LAI-LLM-025`. All of these refuse before any model is touched.
- **Memory is the fit set.** `U0` and `U1` are the summed `vram_used_mib` of the GPUs the fit rules count for the backend (`Snapshot.FitGPUs`: `llama.backend` of `node.yaml`, else detected from the first sample), so a hybrid laptop is measured on the GPU llama uses; an AMD APU's value already includes the GTT (§4.13 implementation note 4). A sample that fails is skipped; fewer than 3 good baseline samples of 5, or no good sample during the request, fails. A peak that is not above the baseline fails (the numbers would be meaningless). One more sample is taken after the request returns.
- **Throughput.** `llama-bench` takes flash attention as `0` or `1`, so `on` becomes `-fa 1`, `off` becomes `-fa 0`, and `auto` leaves its default; `n-gpu-layers = all` becomes `-ngl 99`; an absent value leaves the flag out. The environment is `Options.Env` (the node's `llama.env`), else execx's minimal one. `pp512_tps` and `tg128_tps` are the `avg_ts` of the entries with `n_prompt 512, n_gen 0` and `n_prompt 0, n_gen 128`.
- **MTP acceptance** is `draft_n_accepted / draft_n` of the response `timings` when the server reports them, else the router-log reader `Options.DraftFromLog`, else `null`. `server_tg_tps` is `timings.predicted_per_second`.
- **`disturbed`.** Any `model.loading`, `model.loaded`, `model.unloaded` or `model.failed` event whose `op_id` is not one the run itself received (an event with no `op_id`, such as the watcher's crash report, counts), a `resync` or `shutdown` event, or a stream that closes before the run ends, sets `"disturbed": true`. The result file and the returned `Result` keep the measurements but carry `suggested_*` as `null`, and `Snippet()` is empty. Events are judged when the measurement ends (before the restore): the engine first drains what the stream already delivered, counting a stream already closed as lost, and only then cancels its own `/events` request, so a close it causes itself is never a loss and a real break is never mistaken for it, whenever the watching goroutine happens to be scheduled. A foreign operation that starts in the last instants may be missed.
- **Restore.** The models that were `loaded` or `sleeping` before are recorded when the run starts. On every exit after the first change (success, failure, Ctrl-C) the engine unloads the benchmarked model if it was not loaded before, then loads each recorded model that is not loaded now, in the original order, with a context that ignores the cancellation (each load bounded by 6 minutes). One failed model does not stop the others: `Result.RestoreFailed` names them (the caller prints a warning and `aictl load <id>`), `Result.Restored` lists the rest. After a successful measurement the restore happens before the file is written.
- **Failure** is a `*bench.Error` carrying `LAI-LLM-025` (`LAI-AGT-022` when the cause is a `*BusyError`, `LAI-AGT-021`, `LAI-LLM-008` for the refusals above) and the step (`precheck`, `unload`, `baseline`, `load`, `measure`, `throughput`, `write`). A refusal because a model is `loading` is returned as the bare `*BusyError`. A failed run writes no file.
- **The file** is `<dir>/<id>-<YYYYMMDDTHHMMSSZ>.json` (UTC), one line, written atomically, root 0644 in a 0755 directory (`/var/lib/localai/bench` by default). Beyond the fields of step 6 it may carry `effective_vram_mib` (the router's `memory.effective`, recorded not used) and `gpu_total_mib` (for the catalog comment). On a CPU-only node `gpu` and the four VRAM fields are `null`, and `peak_rss_mib` and `suggested_min_ram_mib` (`ceil(peak x 1.10)`) are set; the peak is the summed `VmRSS` of the processes that appeared after the models were unloaded (the model's child), so the router's own memory is not counted.
- **The snippet** names a short GPU name (`NVIDIA GeForce RTX 2070 with Max-Q Design`, 7982 MiB becomes `RTX 2070 Max-Q 8 GB`), the build (the target of `/opt/localai/llama.cpp/current`, or `Options.Build`) and the UTC date; CPU-only results say `CPU only` and suggest `min_ram_mib`.
- **Rounding** is integer arithmetic, `(measured x 110 + 99) / 100`, so 6581 gives 7240 and nothing is ever rounded below the measurement.

### 4.14 Router watcher

An `app.Worker` (`internal/router/watcher.go`, name `router-watcher`). Every 5 s, and whenever the `/models/sse` stream delivers an event (at most one SSE-triggered poll per 500 ms), the agent reads `GET /models` and diffs it with its last view. `Start` returns at once; the first poll runs on the poll goroutine, so a router that is not up yet does not delay the agent.

**The view.** The last good list, when it was read, and `stale` plus the error text when the last poll failed. Readers (`/status`, `GET /models`) copy it under a lock that no I/O ever holds, so a hung router never blocks them. The first good list is a **baseline**: it publishes no event (a model already loaded at start did not just load), but findings are evaluated on it.

**Events** are edge-triggered and published only for changes outside an agent operation, with no `op_id`:

| Change since the last good list | Event |
|---|---|
| a model that was `loaded` or `sleeping` is now anything else (including `loading`: the child restarted) | `model.unloaded {model, reason: "crash"}` |
| a `loaded` or `sleeping` model is no longer in the list (a reload dropped its section) | `model.unloaded {model, reason: "preset_changed"}` |
| a model becomes `loaded` and was not `loaded` or `sleeping` | `model.loaded {model, load_ms}` |

`load_ms` is measured from the first poll that saw the model `loading`; it is `0` when the load was not observed (the duration is unknown, not zero). `loaded` ↔ `sleeping` is not an event. `model.loading` and `model.failed` belong to the orchestrator (§4.4), which knows the `op_id`.

**Operations.** The orchestrator, key rotation and llama restart call `Suppress(op_id)` while they hold `modelOpsMu` and release it when they finish. While any operation is active, the watcher keeps reading but publishes nothing and does not re-evaluate `LAI-LLM-009` and `LAI-LLM-028` (an evict-then-load passes through states that would raise them); what it reads becomes the new baseline, so nothing the operation did is reported later. A poll that overlapped the start or the end of an operation counts as quiet too (an epoch counter, not a timestamp). The release also nudges a poll.

**Findings** are level-triggered: recomputed from every good list, reported once when they appear (`AlertSink.Raise(code, subject, details)`) and cleared when they stop being true (`Clear`). `ManagerAlerts` connects the sink to the doctor alert manager (`internal/doctor`), which owns severity, title, fix and the `alert.raised` / `alert.cleared` events; those alerts are keyed by code, so the adapter raises a code when its first model appears, re-raises it with the new `models` list when the set changes and clears it when the last one is gone.

| Code | Subject | Raised when | Cleared when |
|---|---|---|---|
| `LAI-LLM-009` | model id | the model's `status.failed` is true | it is not |
| `LAI-LLM-028` | none | more models are `loaded` than `models_max` (not evaluated during an operation; skipped when `models_max` is 0) | not any more |
| `LAI-LLM-024` | none | an entry has `source: cache`, or its id is not in the effective set (`models.ini`) | none is left |
| `LAI-LLM-004` | none | 3 consecutive polls fail with the router not answering (connection, timeout, `502/503/504`): a llama restart takes a few seconds and is not an alert | a poll succeeds |
| `LAI-LLM-005` | none | 2 consecutive polls get `401` (the client has already re-read the key file once per call) | a poll succeeds |

A malformed answer, a missing key file or any other failure marks the view stale and is logged once per episode; it raises no code.

**Failures and backoff.** After `n` consecutive failed polls the wait doubles per failure up to 30 s (5, 10, 20, 30, 30 ... s); one success resets it. `Kick()` (a `key.rotated` event, an operation's release, an SSE event) polls at once. When the router comes back after a restart, the next good list is diffed against the last good one: models that were loaded and are not any more are reported as `crash` (unless an operation was running).

**Key rotation.** On `key.rotated` the watcher makes the client forget its cached key and polls. A rotation the watcher did not hear about is absorbed by the client's one retry after a `401` (§3.6.1 rule 2), so it raises nothing.

**SSE.** The stream is only a nudge and a source of load progress; `OnProgress` hands every event to the orchestrator, which forwards `model.loading {progress}` with its own `op_id` (§4.4 step 6), and `LatestProgress(id)` returns the last progress of a loading model. It reconnects with backoff (1 s doubling to 30 s, reset after an event or a 30 s run); an unavailable stream is logged once per episode and the poll carries on alone. A restart of llama ends the stream, which polls at once.

Known limit: a router that restarts and brings the same models back within one poll interval produces no event (the diff sees `loaded` before and after). The orchestrator's own restarts are suppressed anyway, and the unit's `NRestarts` (the service watcher) records the rest.

## 6. Security considerations
- llama-server binds only `127.0.0.1:8080`; children bind random loopback ports and are reachable only from the router (and other local processes; they carry no key — accepted, loopback-only, same trust as before).
- The API key reaches the process only through systemd `LoadCredential` (`%d/llama-api-key`), never on a command line or in an environment variable; `/proc/<pid>/cmdline` shows the credential path, not the key.
- The unit runs as `localai` with no write access outside `/var/lib/localai`.
- `extra_args` cannot override host/port/key/model (catalog lint) and are rendered as INI keys, never through a shell.
- Builds compile third-party code as root into `/opt`; the source comes from a pinned commit (catalog `kit-llama-cpp`, node.yaml `llama.commit`), verified by the kit's sha256 when taken from the kit.
- Migration never prints the key; it logs the fingerprint only.
