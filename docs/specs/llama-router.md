# Spec: llama-server router (presets, load/unload, builds, migration)

> **Status:** approved design · **Epic:** E2 · **Code:** `agent/internal/router/` · **Doctor area:** `LAI-LLM`
> Canonical names: [overview.md](../architecture/overview.md) §3. Decision: [ADR-0002](../decisions/0002-llama-router-mode.md). Catalog schema: [catalog.md](catalog.md). Agent API: [agent.md](agent.md) §3.8.
> Verified against llama.cpp commit **`f3586e66b`** (2026-10-31): `tools/server/README.md` §"Using multiple models", `tools/server/server-models.cpp`, `common/preset.cpp`, `common/arg.cpp`. Any statement below about router behaviour must be re-verified when the pinned commit changes (§9.3 test R1–R8).

## 1. Purpose and scope

Every node serves its LLMs and VLMs through one `llama-server` process in **router mode** on `127.0.0.1:8080`, unit `localai-llama.service`. This spec defines:
- the exact systemd unit (router mode, and the `single` fallback);
- how the agent **generates** `/etc/localai/models.ini` from the catalog, the profile and `node.yaml`;
- the **fit rules** that decide whether a model may be loaded;
- the **load/unload orchestration** (eviction, readiness, timeouts, rollback);
- which model is loaded at boot;
- how llama.cpp is **built** into `/opt/localai/llama.cpp/builds/<commit>-<backend>` and switched;
- the **migration** from today's hand-made `llama-qwen.service` with zero client changes;
- the `/v1/models` output the gateway relies on;
- the benchmark helper `aictl bench`.

### Non-goals
- Downloading model files (that is [ark-sync.md](ark-sync.md); the router's own `-hf`/`POST /models` download feature is **never** used).
- Choosing which models a profile contains ([catalog.md](catalog.md)).
- whisper.cpp and piper ([companion-services.md](companion-services.md)).
- Per-request routing across nodes ([gateway.md](gateway.md)).
- ROCm/HIP builds (AMD nodes use Vulkan RADV, as on ai-n1 today). A future ADR may add `rocm`.

## 2. Concepts

| Term | Meaning |
|---|---|
| **Router** | `llama-server` started without `-m`. It spawns one child `llama-server` per loaded model on a random loopback port and forwards requests by the `model` field |
| **Preset** | One INI section `[<model-id>]` in `models.ini`. Keys are llama-server args without dashes |
| **Effective model set** | The llama models that get a preset on this node (§4.1) |
| **Loaded set** | Models whose router status is `loaded` or `loading` (and `sleeping`, which we never enable) |
| **Static fit** | Can this model ever load on this hardware? Drives `loadable` in the API |
| **Dynamic fit** | Can it load **now**, given what else is loaded? Drives eviction |
| **Build id** | `<commit>-<backend>`, e.g. `f3586e66b-cuda`. `commit` is the 9-char short sha (`git rev-parse --short=9`) |
| **Legacy alias** | An extra model name kept from the pre-migration unit (e.g. `qwen3.5-9b`), so old clients keep working |

### 3.2 `localai-llama.service` (router mode)

Generated from a Go template (`internal/router/unit.go`). Values in `<>` come from the profile; everything else is fixed. Example for ai-n3 (profile `small-8gb`: `models_max: 1`, `memory_margin_mib: 512`):

```ini
# GENERATED by aiagent — do not edit. Regenerated from node.yaml + catalog profile.
# Spec: docs/specs/llama-router.md §3.2
[Unit]
Description=Local AI llama.cpp router (llama-server, router mode)
Documentation=https://github.com/marinoscar/local-ai/blob/main/docs/specs/llama-router.md
After=network.target local-fs.target
StartLimitIntervalSec=300
StartLimitBurst=5

[Service]
Type=simple
User=localai
Group=localai
SupplementaryGroups=video render
WorkingDirectory=/var/lib/localai
LoadCredential=llama-api-key:/etc/localai/api-key
Environment=LLAMA_CACHE=/var/lib/localai/llama-cache
ExecStart=/opt/localai/llama.cpp/current/bin/llama-server \
  --models-preset /etc/localai/models.ini \
  --models-max <1> \
  --models-memory-margin <512> \
  --no-models-autoload \
  --host 127.0.0.1 \
  --port 8080 \
  --api-key-file %d/llama-api-key
Restart=on-failure
RestartSec=5
TimeoutStartSec=60
TimeoutStopSec=30
LimitMEMLOCK=infinity
# Hardening that does not interfere with GPU access or mmap of model files:
NoNewPrivileges=yes
PrivateTmp=yes
ProtectSystem=strict
ProtectHome=yes
ReadWritePaths=/var/lib/localai
ProtectKernelTunables=yes
ProtectKernelModules=yes
ProtectControlGroups=yes
RestrictSUIDSGID=yes
LockPersonality=yes

[Install]
WantedBy=multi-user.target
```

Rules:
- **No per-model args on the router command line.** Router CLI args have the highest precedence and are inherited by every child (README §Model presets, precedence rule 1). Anything model-specific goes in the preset.
- `--models-memory-margin` is emitted only when the profile's `memory_margin_mib > 0`. It turns on the router's own LRU memory check; the agent's fit rules (§4.3) run first, so the router's check is a second line of defence.
- `ProtectSystem=strict` makes `/srv/localai` and `/media/*` read-only for llama, which is what we want (models are only read). `ProtectHome=yes` is safe because after migration no model lives under `/home`.
- `PrivateDevices` and `MemoryDenyWriteExecute` are **not** set: GPU device nodes must be visible, and the CUDA/Vulkan drivers JIT code.
- `KillMode` stays the default `control-group`, so stopping the unit also stops every child instance.
- `WantedBy=multi-user.target`: llama starts at boot **without** the agent. Inference survives a broken agent.

### 3.3 Environment drop-in

`/etc/systemd/system/localai-llama.service.d/50-env.conf`, generated when the merged environment (§4.2 step 6) is non-empty:
```ini
# GENERATED by aiagent — do not edit. Spec: docs/specs/llama-router.md §3.3
[Service]
Environment=GGML_VK_SUBALLOCATION_BLOCK_SIZE=4294967296
```
Preset files cannot carry arbitrary environment variables (unknown INI keys are rejected by `common/preset.cpp`), and children inherit the router's environment, so per-model `llama.env` from the catalog is merged here. Changing this file requires a router restart; the agent does not restart automatically, it raises `LAI-AGT-016` ("restart llama to apply").

### 3.4 `localai-llama.service` (`single` fallback mode)

When `node.yaml: llama.mode: single` (ADR-0002 risk mitigation), the same unit name runs a classic one-model server for the **current default model**. Same `[Unit]`, `[Install]` and hardening as §3.2; only `ExecStart` differs. ai-n3 example:
```ini
ExecStart=/opt/localai/llama.cpp/current/bin/llama-server \
  -m /srv/localai/models/qwen3.5-9b-q4km/Qwen3.5-9B-Q4_K_M.gguf \
  --alias qwen3.5-9b-q4km,qwen3.5-9b \
  --tags chat,reasoning,coder \
  -c 32768 \
  -ngl 99 \
  --flash-attn on \
  --parallel 1 \
  --spec-type draft-mtp \
  --spec-draft-n-max 3 \
  --host 127.0.0.1 \
  --port 8080 \
  --api-key-file %d/llama-api-key
```
The args come from the same mapping table (§3.5.1). Each INI key is rendered through this key → CLI flag table (keys not listed render as `--<key> <value>`; keys with value `true` render as the bare flag):

| INI key | CLI flag |
|---|---|
| `model` | `-m` |
| `c` | `-c` |
| `n-gpu-layers` | `-ngl` |
| `alias` | `--alias` |
| any other key `k` | `--k` |

The example above is the exact expected rendering (short flags `-m`, `-c`, `-ngl`). In single mode, "load model X" means: rewrite the unit for X, `daemon-reload`, restart, wait for `/health` 200 and `/v1/models` listing X, and roll back to the previous unit on failure (§4.8).

### 3.5 `models.ini` (preset file)

#### 3.5.1 Mapping table: catalog / node → INI keys

| Source | INI key in `[<id>]` | Rendering rule |
|---|---|---|
| `models[].id` | section name `[<id>]` | the section name **is** the router model name and the OpenAI `model` id (ADR-0002) |
| `files[kind=weights]` | `model` | absolute path on the chosen content root (§4.1): `<root>/models/<id>/<name>`. Multi-shard: the `-00001-of-NNNNN` file |
| `llama.ctx` | `c` | integer. Always pinned (so `--fit` cannot grow the context and starve other models; README §Memory-based unloading) |
| `llama.n_gpu_layers` | `n-gpu-layers` | integer, or `all` |
| `llama.flash_attn` | `flash-attn` | `on` \| `off` \| `auto` |
| `llama.parallel` | `parallel` | integer |
| `llama.speculative.type` | `spec-type` | `draft-mtp` \| `draft` |
| `llama.speculative.n_max` | `spec-draft-n-max` | integer |
| `llama.speculative.draft_file_kind` (non-null) | `model-draft` | absolute path of `files[kind=draft]` |
| `llama.speculative.draft_ngl` | `spec-draft-ngl` | only when `model-draft` is emitted; `all` or integer |
| `llama.mmproj_file_kind` (non-null) | `mmproj` | absolute path of `files[kind=mmproj]` |
| `llama.chat_template` = builtin name | `chat-template` | string |
| `llama.chat_template` = a file kind | `chat-template-file` | absolute path of that file |
| `llama.extra_args[]` | one key per arg | `--foo bar` → `foo = bar`; `--foo` (flag) → `foo = true`; `--no-foo` → `no-foo = true`; `-x v` → `x = v`. The linter (catalog.md §2) already refuses host/port/api-key/model/models-*/alias/-hf |
| `roles[]` | `tags` | comma-joined in catalog order, e.g. `chat,reasoning,coder`. Informational in `/v1/models` |
| `node.yaml: llama.legacy_aliases[<id>]` | `alias` | comma-joined. The router registers them as routing aliases (`server-models.cpp`: aliases parsed from the preset's `alias`, conflict-checked against other names) |
| effective default model (§4.6) | `load-on-startup` | `true` in the default model's section only |
| fixed | `stop-timeout` | `10` in `[*]` |
| fixed | `load-on-startup` | `false` in `[*]` |
| `llama.env` | — | **not in INI**; merged into the drop-in §3.3 |
| `requirements.*`, `client_hints.*`, `summary*` | — | not rendered (used by fit rules, snippets and the gateway) |

Rendering is deterministic: sections sorted by model id (default first is **not** used, to keep diffs stable); keys in the table order; values never quoted; paths are validated to contain no `;`, `#`, newline or leading/trailing spaces (else `LAI-LLM-007`).

#### 3.5.4 How the file is rendered (`internal/router`, ROUTER-03)

`router.BuildPreset` renders one model's section, `router.Render` the file, `router.MergeEnv` and `router.RenderDropIn` the drop-in. They are pure; `router.Generator` (§4.2) wraps them with the disk, the state store and the router. The rules the mapping table leaves open:

- **Which file.** `files[kind=K]` is the one file of kind `K`. A model that lists several files of one kind (the shards of a split GGUF) is given the one whose name ends in `-00001-of-NNNNN.gguf`; several files and not exactly one first shard is an error (`LAI-LLM-007`). A file name must be a clean relative path (no leading `/`, no `..`, no `./`): the preset never points outside `<root>/models/<id>/`.
- **Which keys.** A key is written only when its catalog field is set: `n_gpu_layers: 0` is written (`n-gpu-layers = 0`), an absent `n_gpu_layers` is not. `spec-draft-n-max` is written only when `n_max` is above 0. `llama.speculative.draft_ngl` is written only together with `model-draft`. `llama.mmproj_file_kind` and `draft_file_kind` name the *kind* of the file to look up, so a catalog that names a kind it has no file for is an error.
- **`extra_args`.** Each list entry is split at its first space or `=`; an entry that is not a flag is the value of the previous flag (`["--temp", "0.7"]` equals `["--temp 0.7"]`; a negative number is accepted there as a value). The key is the flag without its one or two leading dashes, so `-ub 512` gives `ub = 512`. A flag without a value is `true`. The agent refuses again what lint refuses (host, port, `api-key*`, `-m`, `--model`, `--models-*`, `--alias`, `-hf`), and also the keys it writes from other fields (`model-*`, `mmproj*`, `tags`, `load-on-startup`, `stop-timeout`, `version`) and a key that duplicates one the section already has (`-c 8192` next to `ctx`): an unsafe or ambiguous entry makes the model's section fail, not the file.
- **Unsafe text.** A path, an alias or an `extra_args` value containing `;`, `#` or a control character is refused, as is a path that is not absolute or has leading or trailing white space. Header values (node id, profile id, catalog version) are reduced to letters, digits and `. _ - : +` so they cannot break out of the comment line.
- **Aliases.** `legacy_aliases[<id>]` becomes `alias`. An alias that is not a valid name, equals a section name or is already taken by a model that sorts earlier is left out and reported as `LAI-LLM-007` (`details.alias`), because the router checks aliases for conflicts and a refused file would leave every model unloadable. An alias of a model that is not in the file is ignored.
- **`inputs_sha256`** is the sha256 of the canonical JSON (fixed field order, sorted map keys and lists, no HTML escaping) of: the renderer version, node id, profile id, catalog version, the profile overrides' add and remove lists, the effective default, and for every model in the file its id, chosen root, roles, `llama` block without `env`, file kinds and names, and aliases. It therefore changes when a section changes and not when a field the table does not render changes (a summary, a `client_hints`, a `llama.env`).
- **Comparison.** Two renderings are compared without their first line (time and agent version). Everything else, including the `inputs_sha256` line, is compared.
- **Golden files.** `internal/router/testdata/golden/ai-n3.models.ini` and `ai-n1.models.ini` hold the files of §3.5.2 and §3.5.3 as `Generator` renders them for those catalogs, with a fixed clock, so even the first line is byte-identical. The one value a golden file cannot hold is the 64-hex hash (a digest-shaped literal trips the secret scanners), so the test replaces it with `<sha256>` in both sides before comparing and checks the hash separately. Regenerate with `go test ./internal/router -run Golden -update` and read the diff.

**Environment drop-in.** `MergeEnv` takes the models that are in the file (a model that was dropped contributes nothing) and `node.yaml llama.extra_env`. The node's value wins, even over a conflict. `LLAMA_ARG_*` is refused from both sources (the router sets those; an inherited one would override its arguments), as is a name that is not valid (catalog: any environment variable name; node: `^(GGML|LLAMA|CUDA)_[A-Z0-9_]+$`) and a catalog value that is not one line. A refusal is `LAI-LLM-007` with `details.source`; a refused value is never recorded. `RenderDropIn` writes `Environment=NAME=value` lines sorted by name; a value with white space, quotes or a backslash is written as `Environment="NAME=value"` with those escaped, and `%` is doubled (systemd expands specifiers in unit files).

### 3.6 Router API used by the agent

All calls go to `http://127.0.0.1:8080` with `Authorization: Bearer <key>` (every route except `/health` requires the key, `server-http.cpp` public endpoint list). HTTP client timeout 5 s per call unless stated.

| Call | Purpose | Notes |
|---|---|---|
| `GET /health` | liveness | public (`/v1/health` too); `200 {"status":"ok"}`, or `503` with an error object while the model of a single-mode server is loading |
| `GET /models` | status of every preset | `data[].id`, `aliases`, `tags`, `status.value` ∈ `unloaded\|loading\|loaded\|sleeping\|downloading\|incomplete`, `status.failed`, `status.exit_code`, optional `memory.{min,max,effective}` (with `--models-memory-margin`) |
| `GET /models?reload=1` | re-read `models.ini` and reconcile | a **running** model whose preset changed or was removed is **unloaded** by the router (`server-models.cpp` reload path). See the reload-safety rule §4.2 step 8 |
| `POST /models/load` `{"model": "<id>"}` | start a child | returns `{"success": true}` immediately; readiness is observed via `GET /models` |
| `POST /models/unload` `{"model": "<id>"}` | stop a child | child gets `stop-timeout` (10 s) then is force-killed |
| `GET /models/sse` | progress events (`model_status` / `status_change` with `progress.stages/current/value`) | optional; used for UI progress and to nudge the watcher, never for correctness. Frame format in §3.6.1 |
| `GET /v1/models` | the OpenAI list | in router mode this is the same handler as `/models` |
| `GET /props?model=<id>` | `n_ctx`, build info of a loaded model | doctor checks only |
| `POST /v1/chat/completions` | doctor/drill smoke test | `max_tokens: 8` |

Never used: `POST /models` (download), `DELETE /models`, `?autoload=true`.

#### 3.6.1 The client (`internal/router`, ROUTER-01)

The wire facts below were checked against `tools/server/README.md`, `server-models.cpp` and `server-http.cpp` at llama.cpp commit `f3586e66b`; the manual checks R9 and R10 (§9.3) re-verify the two that matter most after a commit change.

**Shapes.**
- `status.value` is one of `unloaded`, `loading`, `loaded`, `sleeping`, `downloading`, `downloaded`, `incomplete`. A value outside the list is kept as is and treated as "not running" (logged once per change); it is never a parse error, so a llama.cpp upgrade cannot blind the watcher.
- `status.failed: true` and `status.exit_code` appear **only** when the model is not running and its child exited with a non-zero code (the router's `is_failed`). A model that was never started has neither.
- `status.args` is the child's command line (no key: the router strips it); `status.preset` is the INI section text; `status.progress` is, for a downloading model, a map `URL → {done, total}`. Loading progress is **not** in `GET /models`, only on the SSE stream.
- `source` is `preset`, `models_dir` or `cache`; `aliases` and `tags` are lists; `context_length` is the training context. `architecture.{input,output}_modalities` are lists of strings.
- `memory` exists only with `--models-memory-margin`: `{status, min, max, effective}`, each estimate `{n_ctx, devices: [{kind: "device"|"host", name, total, free, model, context, compute}]}` in **bytes**; `effective` is `null` unless the model is loaded. The planner's `used_v(k)` is the sum of `model + context + compute` over the entries of kind `device`, rounded up to MiB (`ModelStatus.EffectiveMiB`); the `host` entry is RAM and is ignored.
- Decoding is strict about shape (a body that is not an object with a `data` array, an entry without `id` or `status.value`, a duplicate id, a wrong type, a negative size, trailing data, a body over 8 MiB: `ErrMalformed`) and tolerant about content (unknown fields and unknown values are ignored).
- Errors are `{"error": {"code", "message", "type"}}`. `POST /models/load` of a running model is `400` ("model is already running"), of an unknown model `404`; `POST /models/unload` of a model that is not running or unknown is `400`. A wrong or missing key is `401` ("Invalid API Key", `authentication_error`).
- SSE: `Content-Type: text/event-stream`, one `data: <json>` line plus a blank line per event, **no** `event:` line. The JSON is `{"model": "<id>" | "*", "event": "<name>", "data": {...}}`. Names seen: `model_status` (the first, at spawn), `status_change` (every later change; `data.status`, `data.exit_code` with `unloaded`, `data.progress {stages, current, value}` while loading), `download_progress`, `download_finished`, `download_failed`, `model_remove`, `models_reload` (model `*`), `model_memory`. The README documents `model_status` only; the client treats `model_status` and `status_change` alike and skips a frame it cannot use without ending the stream. A line over 1 MiB ends the stream.

**Rules.**
1. **Base URL and key.** `http://127.0.0.1:<llama.port>`; the client refuses any base URL that is not plain `http` on a loopback address (no credentials, path or query). The key is read from `/etc/localai/api-key`, re-read when the file's mtime or size changes, after `key.rotated` and after a `401` (§4.11), and sent only as `Authorization: Bearer`. `/health` is sent without it. The key never appears in a log line, an error, an event or a finding: logs carry its fingerprint (last four characters). A key file that is missing, not a regular file or holds an unusable value fails the call before anything is sent.
2. **A `401` is retried once**, and only when re-reading the key file gives a different key (the key was rotated between two reads). An unchanged key is a real `401`: `LAI-LLM-005`, never retried.
3. **Transport hardening.** The proxy environment is ignored; the dialer connects only to loopback addresses; a redirect is never followed (it is an error); response bodies are capped (8 MiB for `GET /models`, 1 MiB otherwise); compression is off.
4. **Timeouts.** 5 s per call; `POST /v1/chat/completions` (the smoke test) 30 s, because it generates tokens and a CPU node is slow; the SSE stream has no overall timeout, only 5 s to receive its headers.
5. **Error classes.** Connection refused or reset, a timeout, or `502`/`503`/`504` is `ErrDown` (`LAI-LLM-004`); `401` is `ErrUnauthorized` (`LAI-LLM-005`); `404` is `ErrNotFound`; any other non-2xx is an `*HTTPError` with the router's message (scrubbed, at most 200 bytes); an unusable body is `ErrMalformed`. A call cancelled by its caller returns the context error, not `ErrDown`.
6. **Allow list.** The client can issue only the routes of the table above. A download (`POST /models`), a delete (`DELETE /models`) and any `autoload` query are refused with `ErrRefused` before anything is sent; the tests assert it on the request log of the fake router.
7. **The fake.** `internal/router/fake` is a router served over HTTP with scripted model states (`Set`, `Crash`, `FailLoad`, `Restart`, load time), failure modes (`Down`, `Reset`, `Delay`, `Malformed`, `Force`, `Redirect`), a key that can be rotated, an SSE stream (`Emit`, `DropStreams`) and a request log that records method, path, query and whether a correct key was sent (never the key). Other packages' tests reuse it.

## 4. Behaviour

### 4.1 Effective model set and file location

For each catalog model `m` with `engine: llama`:
1. `m` is **in scope** if it is in the profile's `include.models` ∪ `profile_overrides.add_models` − `remove_models`, **or** it is present on any mounted content root (a stored model may still be loaded; ADR-0005 "serve directly from the drive"). `profile_overrides.remove_models` only removes `m` from the desired set (sync stops fetching it, boot does not load it); a removed model that is still present on disk **stays in scope** (it keeps a preset, is listed and loadable) until it is deleted (`aictl delete`).
2. `m` is **present** on a root if `<root>/models/<id>/MANIFEST.json` lists every `files[]` entry with matching sha256 and `verified_at` set ([ark-sync.md](ark-sync.md) §4.11). Concretely (`router.ManifestPresence`): `item_id` is the model id, `state` is `verified`, `verified_at` is an RFC 3339 time, and every catalog file has a manifest entry with the same `path` (and `kind`, when the manifest gives one) and the same sha256 (case-insensitive). A catalog file without a pinned sha256 cannot be verified, so the model is not present. Chosen root: internal (`/srv/localai`) if present there, else the first mounted ark drive (sorted by mount path); a copy on the internal root that is not verified does not hide a verified copy on a drive.
3. `m` gets a preset iff in scope **and** present **and** statically fits (§4.3.2). Others are absent from `models.ini`, so neither the WebUI dropdown nor a direct client can ask for them.

### 4.2 Preset generation (`router.Generator.Generate`)
Triggered at agent start, on catalog refresh, `PUT /profile`, `PUT /models/default`, `node.yaml` change of `llama.*`, `drive.mounted`/`drive.unmounted`, a model becoming verified or deleted, and a build switch. Calls are serialised. The caller assembles the inputs (`router.Inputs`: node id, catalog, profile, `profile_overrides`, `node.yaml llama{}`, mounted roots, the fit `Env`, `state.models.default`, survival flag); `Generate` returns an error only when `models.ini` is not in the state the inputs call for (it cannot be rendered, read, saved aside or written). A failure to apply the file to a running router, or to write the drop-in, is in the `Result` and retried by the next call.
1. Compute the effective set (§4.1) and the effective default (§4.6).
2. Render sections (§3.5.1) and the header (`inputs_sha256` = sha256 of the canonical JSON of the inputs, §3.5.4, so identical inputs give byte-identical output except the first line, which is excluded from comparisons). A model whose entry cannot be rendered (a bad catalog entry or an unsafe path, `LAI-LLM-007`) is **left out on its own**; the other models are still written.
3. Validate: every path exists and is readable by uid `localai` (`faccessat` with `AT_EACCESS` after `setfsuid` is not available in pure Go; instead check mode bits + ownership along the path: each directory from `/` down `o+x` or owned/grouped by localai with the matching bit, the file a regular file with `o+r` or owned/grouped by localai with the matching bit; `router.CheckReadable`). Failure → drop that model, `LAI-LLM-008` with `details.path` and `details.reason` (`missing`, `not_a_file`, `directory_not_searchable`, `file_not_readable`, `stat_failed`). The default (§4.6) is chosen among the models that survive steps 2 and 3, so a default that was dropped falls back to the next rule, and with none `LAI-LLM-014` is raised.
4. Read the current file. If its sha256 ≠ `state.llama.ini_sha256` (someone edited it) → save it as `models.ini.hand-edited-<ts>` (`-2`, `-3` … when the name exists) and raise `LAI-LLM-006` (warning). Refinements: with **no** recorded hash (a fresh state file), a file that carries the `GENERATED by aiagent` header is ours and a file without it is foreign and saved; a file whose body (minus the first line) already equals the new rendering loses nothing and is not reported (a crash between the rename and the state update looks like an edit); if the copy **cannot be written, the file is not overwritten** (`LAI-LLM-007`, error returned): nothing is destroyed that could not be kept.
5. If the rendered body (minus the first line) equals the current file → **do not write** (step 7 is skipped, and the recorded hash is corrected if it was stale); steps 6 and 8 still run.
6. Merge env: union of `llama.env` over models in the file, plus `node.yaml llama.extra_env` (node wins). Two models setting the same key to different values and no node value → drop the key, `LAI-LLM-015`. Render the drop-in (§3.3) and compare it with the file on disk **on every run, whether or not `models.ini` changed** (an `extra_env` edit changes only the drop-in); if it differs, write it (mode 0644; the directory is created if needed), or remove it when the merged environment is now empty, run `daemon-reload` through the systemd manager and raise `LAI-AGT-016` (details `target: llama`). The router is never restarted. A drop-in that cannot be written is `LAI-LLM-007` (`subject: drop-in`) and does not stop `models.ini`.
7. Write `models.ini` atomically (`config.WriteFileAtomic`: temp file, fsync, rename, directory fsync; root:localai 0640), keeping the previous file as `models.ini.prev` first (a failure to keep it is logged and does not stop the write), and update `state.llama.ini_sha256` (sha256 of the file as written, first line included). A write that fails (unwritable directory, `ENOSPC`, rename) leaves the old file and the recorded hash untouched and raises `LAI-LLM-007`; an `ErrNotDurable` (only the final directory sync failed) is treated as written. A state update that fails is logged; the next run recognises the file as its own and records the hash.
8. **Reload-safety rule** (pure: `router.DecideReload`). If the router is up, compare, for every model whose router status is `loaded`, `loading` or `sleeping` (`Status.Running`), the **old** and the new sections. The old sections are what the router **last read**, not necessarily what was on disk: when a reload is skipped because only `load-on-startup` differs, the router still holds the older file, so the generator keeps that older parse as the base for the next comparison (after an agent restart, or a router that was down, the file on disk before this write stands in for it).
   - only `load-on-startup` differs (a default change) or nothing differs → **do not** call reload when no section was added/removed either; the file is correct for the next router start. Otherwise reload is safe.
   - any other key differs for a running model (a change in `[*]` or `version` counts for every model) → take `modelOpsMu` (waiting up to 60 s; if it stays busy the reload is retried by the next run and the result carries the error), read the statuses again, call `GET /models?reload=1` (the router unloads that model), emit `model.unloaded {reason: "preset_changed"}` for it (with the watcher suppressed for the duration, so it is not reported twice), wait until the router has stopped it (at most 20 s), then re-load it through §4.4 while still holding the lock (`ModelLoader.LoadHeld`; until the orchestrator exists, a plain `POST /models/load`). A model that the router kept running is not loaded again.
   - a running model whose **section was removed** (its files vanished, an ark drive was pulled, it was deleted) → the same reload; the router unloads it, `model.unloaded {reason: "preset_changed"}` is emitted for it and it is **not** loaded again (it has no preset).
   - sections added or removed, or changed, only for non-running models → `GET /models?reload=1`.
   - a running model that the old file did not have (a hand edit, a lost reload) cannot be proven unchanged and is treated as changed.
   - after any reload, the models the rule meant to protect (running, section unchanged) are checked; one that the router unloaded anyway (it may judge a `load-on-startup` difference it never read as a changed preset) is reported with `model.unloaded {reason: "preset_changed"}` and loaded again.
   - **Resync.** The first run after an agent start (or after the router was seen down) compares the ids the router lists with `source: preset` (cache models are not ours) with the sections of the file; if they differ the router is reloaded even though the file did not change (the reload that should have followed the last write never happened). The same applies after a reload that failed.
9. If the router is down (`ErrDown`), nothing else to do; the next start reads the new file. Any other router error (`LAI-LLM-005`, a malformed answer) is returned in the `Result` and the apply is retried by the next run.

**Findings.** `Generate` raises through the alert sink and clears what a later run no longer finds: `LAI-LLM-007` (subjects: the model id, `alias:<a>`, `env:<KEY>`, `drop-in`, or the failed step), `LAI-LLM-008` (the model id), `LAI-LLM-014`, `LAI-LLM-015` (the variable). `LAI-LLM-006` and `LAI-AGT-016` are events: raised where they happen and not cleared by `Generate` (an agent restart, or the operator's acknowledgement in the doctor, clears them).

### 4.3 Fit rules (`router.Fit`)

#### 4.3.1 Inputs
From `internal/hardware` (agent.md §4.4) and the profile:

| Symbol | Value |
|---|---|
| `B` | node backend (`cuda` \| `vulkan` \| `cpu`) |
| `G_total` | cuda: VRAM total of the GPU(s) (sum when several); vulkan dedicated: VRAM total; vulkan **unified** (agent.md §4.4.2): GTT total; cpu: 0 |
| `G_others` | GPU memory used by processes that are not children of `localai-llama` (measured, 10 s cache) |
| `M` | `router.memory_margin_mib` from the profile (default 512) |
| `R_total`, `R_avail` | `MemTotal`, `MemAvailable` (MiB) |
| `R_res` | RAM reserve: 2048 MiB, or 4096 MiB on unified-memory nodes |
| `need_v(m)`, `need_r(m)` | `requirements.min_vram_mib`, `requirements.min_ram_mib` |
| `used_v(k)` | for a loaded model `k`: the router's `memory.effective` device total in MiB when reported, else `need_v(k)` |
| `N` | `router.models_max` |

**How it is built** (ROUTER-02, `internal/router`: `fit.go`, `plan.go`, `codes.go`; pure, no I/O). `router.NewEnv(snapshot, backend, profile.Router, W_res)` distils a `hardware.Snapshot` into the symbols above: `G_total` is `Snapshot.FitMemory(B)`, `G_others` is `Snapshot.OthersMiB(B)` (a GPU whose share cannot be measured counts 0), unified is `Snapshot.UnifiedMemory(B)`, `R_total`/`R_avail` are `Snapshot.RAM`. `B` is the node's `llama.backend` or, when empty, the detected one (`cpu` when nothing is known). `router.memory_margin_mib` unset (0) is the default 512. A loaded model's `used_v` falls back to `need_v` when the router's `memory.effective` is absent or not positive. Callers refresh the snapshot before planning (it is at most 10 s old), and `G_others` is never read for static fit.

#### 4.3.2 Static fit (the API's `loadable`)
Evaluated in order; the first failing rule gives `loadable_reason`:
1. `B ∈ requirements.backends`, else `LAI-CAT-005` "This model does not run on <B>".
2. GPU backends: `need_v(m) ≤ G_total − M`, else `LAI-CAT-005` "Needs X GB of graphics memory; this computer has Y GB".
3. Unified memory: also `need_r(m) ≤ R_total − R_res`.
4. CPU backend: `need_r(m) ≤ R_total − R_res`.
5. All backends: `need_r(m) ≤ R_total`.
6. Present (§4.1 step 2), else `LAI-LLM-008`.
`G_others` is deliberately ignored here: a desktop session using 300 MiB must not make a model "never loadable".

**Other engines** (`whisper`, `piper`): the same rules run for every catalog model in `GET /models`, but rule 2 is skipped, because these engines have no graphics-memory requirement (`min_vram_mib` is 0 for them by [catalog.md](catalog.md) §2, and a stray value is ignored). `router.Env.Loadable` and `LoadableAll` (`internal/router/loadable.go`) apply this.

**Messages.** `router.Env.StaticFit` returns `loadable_reason` as `{code, message}` (agent.md §3.8.7) plus the Spanish text (`Reason.Text("es")`; the doctor localization hook of AGENT-11 replaces the two in-package texts when it lands). Sizes are decimal GB with one decimal (`MiB × 1048576 / 1e9`; Spanish uses a decimal comma):

| Rule | English message | Code |
|---|---|---|
| 1 | `This model does not run on <B>.` | `LAI-CAT-005` |
| 2 | `Needs X GB of graphics memory; this computer has Y GB.` (X = `need_v(m)`, Y = `G_total`, not `G_total − M`) | `LAI-CAT-005` |
| 3, 4 | `Needs X GB of memory, and the system keeps Z GB for itself; this computer has Y GB.` (X = `need_r(m)`, Z = `R_res`, Y = `R_total`) | `LAI-CAT-005` |
| 5 | `Needs X GB of memory; this computer has Y GB.` | `LAI-CAT-005` |
| 6 | `The files of this model are missing or not verified on this computer.` | `LAI-LLM-008` |

`LAI-LLM-004` (router down) is never produced by the fit rules: the API layer sets it when it cannot reach the router.

#### 4.3.3 Dynamic fit (at load time)
For a candidate keep-set `K` (models that stay loaded):
- count: `|K| + 1 ≤ N`;
- GPU backends: `need_v(m) + Σ_{k∈K} used_v(k) + G_others + W_res + M ≤ G_total`, where `W_res` is the whisper VRAM reservation ([companion-services.md](companion-services.md) §4.2.3): the resolved whisper model's `requirements.min_vram_mib` when whisper's device resolves to `gpu` **and** `localai-whisper` is not running yet; `0` otherwise (when whisper runs, its memory is already measured in `G_others`, so it is not counted twice);
- unified/CPU: `need_r(m) + Σ_{k∈K} need_r(k) ≤ R_avail + Σ_{e evicted} need_r(e) − R_res`.

A unified-memory node is a Vulkan node, so it must satisfy **both** the GPU rule (against the GTT) and the RAM rule; a dedicated Vulkan card and CUDA are subject to the GPU rule only, a CPU node to the RAM rule only. The RAM rule is deliberately conservative: `Σ_{k∈K} need_r(k)` is counted on top of `R_avail` (mapped weights are reclaimable page cache that `MemAvailable` already counts as free), and an evicted model's `need_r` is credited back. It never over-commits; at worst it evicts one model more than a precise measurement would.

**Eviction planner** (`Env.Plan(m, loaded, unloadOthers) (evict []string, warn *Reason, err error)`): start with `K = loaded set`. While dynamic fit fails: if `unload_others == false` → fail `LAI-LLM-011`; else remove from `K` the least recently used model (by `state.models.last_used`; ties: larger `used_v` first). If `K` is empty and it still fails on `G_others` alone → load anyway with warning `LAI-HW-005` (the router's `--fit` will reduce offload rather than crash), because refusing would leave the node with no model at all.

Details the code fixes (ROUTER-02):
- **Order of the checks.** When `K` is empty there is nothing to unload, so the load-anyway rule applies even if `unload_others` is `false`; `LAI-LLM-011` is only raised while models are still kept. The failing predicate with `K` empty is `G_others + W_res` (the static fit already guaranteed `need_v(m) + M ≤ G_total`), and the warning is `LAI-HW-005` whenever the GPU rule is short.
- **RAM-only shortage.** If, with `K` empty, only the RAM rule (CPU or unified node) fails because other programs hold the memory, the load also goes ahead, with warning `LAI-HW-006`, for the same reason (a node must not be left with no model; the kernel reclaims mapped pages, and `LAI-LLM-027` covers an OOM kill).
- **Result.** `evict` lists the models to unload in unload order (LRU first); it is empty, never nil, when nothing has to go. The planner applies nothing (ROUTER-05 does) and returns `*router.PlanError` (a `Reason` with `LAI-LLM-011`) for a refusal. `warn` is a `Reason` (code, English and Spanish text); the evictions in `evict` still apply when it is set.
- **Tie-breaks.** `last_used` ascending (never used is the oldest), then larger `used_v`, then model id ascending, so the plan does not depend on the order the caller lists the loaded models.
- **No pin.** There is no pinned or protected model: the default model is evicted like any other when it is the least recently used (R8 in §9.3 evicts the default 9B for the VLM). A model keeps its place only by being more recently used, or by `unload_others: false`.
- An entry for `m` itself in the loaded set is ignored (the orchestrator answers "already loaded" in §4.4 step 3 before planning), and a duplicate id counts once. A `models_max` below 1 counts as 1 (lint `LAI-CAT-018` rules it out).

`unload_others: true` (the default) therefore means "unload as many other models as needed, least recently used first", not "unload everything".

### 4.4 Load orchestration (`router.Load(id, wait, unloadOthers)`)

```
          ┌──────────┐ try modelOpsMu    ┌──────────┐ plan ok   ┌──────────┐ all unloaded  ┌─────────┐
request ─►│ checking │──────────────────►│ planning │──────────►│ evicting │──────────────►│ loading │
          └────┬─────┘ busy → 409         └────┬─────┘           └────┬─────┘               └───┬─────┘
               │ 404/422                       │ 409 LLM-011           │ unload timeout          │
               ▼                               ▼                       ▼                         ├── status loaded ──► READY (200)
             error                           error                 rollback                      ├── failed:true / exit ─► cleanup ─► rollback
                                                                                                  └── timeout ─────────► cleanup ─► rollback
  rollback: reload evicted models (most-recent first) ─► RESTORED (500 LAI-LLM-009 / 504 LAI-LLM-010)
                                                      └► nothing loads ─► load default ─► survival list ─► FAILED (500 LAI-LLM-012)
```

Steps:
1. **Check** (no lock): id exists and `engine == llama` (else `404`/`422`); static fit (`422 LAI-CAT-005`/`LAI-LLM-008`); router `/health` 200 (else `502 LAI-LLM-004`). Mode `single` → §4.8.
2. **Lock:** `modelOpsMu.TryLock()`; busy → `409 LAI-AGT-022` with the running `op_id`. (Cloud jobs and `survival_models` wait up to 60 s instead.) Create `op_id`, audit `model.load`.
3. **Snapshot:** `GET /models`. If `id` is `loaded` → release, `200 {already_loaded: true}`. If `loading` (started by someone else) → skip to step 6 (wait).
4. **Plan** (§4.3.3) → `evict` list. Record `previous = loaded set` and `state.models.last_load = {id, op_id, result: "in_progress"}` (fsync; used by crash-resume logic in agent.md §4.2.4).
5. **Evict:** emit `model.loading {model: id, unloading: evict}`. For each `e`: `POST /models/unload {model: e}`, then poll `GET /models` every 500 ms until `e` is `unloaded` (max 30 s). Timeout → treat as failure (go to rollback with nothing new loaded). Emit `model.unloaded {model: e, reason: "evicted"}`.
6. **Load:** `POST /models/load {model: id}` (non-2xx → failure). Poll `GET /models` every 1 s:
   - `status.value == "loaded"` → success;
   - `status.value == "unloaded"` with `failed: true` (or the child exited) → failure (`exit_code` into `details`);
   - deadline `T = llama.load_timeout_seconds` (default 300 s; ×2 when the weights are on an ark drive) → failure (timeout).
   While waiting, `/models/sse` progress (`progress.value`) is forwarded as `model.loading {progress}` at most once per second.
   With `wait: false`, steps 5–8 run in a goroutine after answering `202`.
7. **Success:** `last_used[id] = now`; `state.models.desired_loaded = loaded set` (order = most recent first); `last_load.result = ok, load_ms`; emit `model.loaded`; trigger state push; release lock; `200`.
8. **Failure → cleanup → rollback:**
   1. `POST /models/unload {model: id}` (ignore errors) and wait ≤ 30 s.
   2. Restore every model in `evict` (most recently used first) with the same procedure as step 6 (each its own timeout). Models never evicted are still loaded and are not touched.
   3. If after that **no LLM is loaded** and the effective default ≠ `id` → load the default. In survival mode, if that fails too, walk the profile's `survival.models` list.
   4. Result: something restored → `500 LAI-LLM-009` (failed) or `504 LAI-LLM-010` (timeout) with `details.rolled_back: true, restored: [...]`; nothing loaded at all → `500 LAI-LLM-012` (critical alert).
   5. `last_load.result = failed|timeout`, emit `model.failed`, release lock.

**Never** loop: a rollback load that fails is not rolled back again.

### 4.5 Unload (`router.Unload(id)`)
Lock as in §4.4 step 2. `POST /models/unload`, poll until `unloaded` (≤ 30 s). If the router still reports it running after 60 s → `systemctl restart localai-llama`, then restore the remaining `desired_loaded` set and raise `LAI-LLM-031`. On success: remove `id` from `desired_loaded`, emit `model.unloaded {reason: "request"}`. The default model may be unloaded; `state.models.default` is unchanged.

### 4.6 Default model and boot
- **Effective default** = `state.models.default` if set and it has a preset; else the profile's `default_model` if it has a preset; else (survival mode) the profile's `survival.default_model`; else none (`LAI-LLM-014`).
- The effective default's section carries `load-on-startup = true` (§3.5.1). So **the router loads the default model by itself at boot**, before the agent is even running. If the default is not loadable at all, no section has the flag.
- After the agent starts (agent.md §4.1 step 14), it reconciles: wait for router `/health` (≤ 120 s), then for the default's status to leave `loading` (≤ load timeout). If the default is not `loaded`, load it via §4.4 (failure → `LAI-LLM-013`). Then load the rest of `desired_loaded` (most recent first) while `models_max` and dynamic fit allow, with `unload_others: false` (boot never evicts). In survival mode the survival set replaces `desired_loaded` if no LLM is loaded.
- `models_max ≥ 1` is guaranteed by catalog lint (`LAI-CAT-018`, [catalog.md](catalog.md) §7), so the router never rejects startup for too many `load-on-startup` models.

### 4.7 Autoload is disabled (`--no-models-autoload`)
The unit always passes `--no-models-autoload`; the profile field `router.autoload` exists only so that this is explicit, and catalog lint requires it to be `false` ([catalog.md](catalog.md) §4, §7).

By default the router starts any model named in a request. We turn that off, because:
1. a stray request (a client with a stale model name, a WebUI dropdown click, a gateway retry) could evict the survival model or OOM an 8 GB laptop without the fit rules running;
2. loads must be serialized, audited and rolled back by the agent (§4.4), which only happens on the agent's path;
3. `models_max` LRU eviction inside the router would silently unload the model an operator just chose.
Consequence: a request for an unloaded model gets an error from the router. Clients see a clear message; the gateway only routes to models reported `loaded` (§4.12). The WebUI dropdown still lists every preset; selecting an unloaded one shows the router's error. Operators load models through the agent (`aictl load`, desktop, Portal, cloud). `--sleep-idle-seconds` is also **not** used (a sleeping default model would make the first request after idle slow and confuse the Portal); see §11.

### 4.8 `single` fallback mode
- Selected by `node.yaml: llama.mode: single`. The agent generates §3.4 instead of §3.2 and does not write `models.ini` (it leaves the last one in place).
- Status: `GET /v1/models` (lists the one model and its aliases) replaces router `GET /models`; the model is `loaded` when `/health` is 200 and the id is listed.
- Load X: lock; if X is current → `already_loaded`; else back up the unit, render the unit for X, `daemon-reload`, `systemctl restart`, wait `/health` 200 + X listed (deadline = load timeout). Failure → restore the previous unit, restart, wait, `500 LAI-LLM-009` (rolled back) or `LAI-LLM-012`. Success → `state.models.default = X` (in single mode the loaded model **is** the default).
- Unload in single mode → `409 LAI-AGT-023` ("single mode always has exactly one model"), unless `force`, which stops the unit.
- Switching `router ↔ single` = edit `node.yaml`; the agent regenerates the unit, `daemon-reload`, restarts llama and restores the default. `LAI-LLM-023` (info) while single mode is active.

### 4.9 Migration from `llama-qwen.service`

Today every node runs a hand-written `/etc/systemd/system/llama-qwen.service` (user `marinoscar`, binary under `~/llama.cpp/build-*`, model under `~/models`, key at `/etc/llama-qwen/api-key`, port 8080, Tailscale Serve to 8080). The migration replaces it with `localai-llama.service` **in place**: same port, same key, same Tailscale Serve, same public URL, and the old model name still works. Clients (Open WebUI via the VPS vhost, OpenCode on the node, the gateway) need **no change**.

Entry point: `sudo aiagent migrate llama-qwen [--dry-run]` (agent.md §3.1), called by `install-node.sh` on nodes that have `llama-qwen.service` ([installer.md](installer.md) §4.3 P8). Every step is idempotent and its progress is recorded in `/var/lib/localai/migration/llama-qwen/progress.json` (`{step, at, t0?}`); re-running continues from the recorded step. Downtime of inference is only between M6 and M7 (typically 10–30 s: the model load time).

**Single writer rule:** a non-dry run first stops `localai-agent.service` (if running) so that `node.yaml`, `state.json` and `models.ini` have one writer, and starts it again after M10 or after a rollback (the agent then reconciles normally, agent.md §4.1). Inference is not affected: `llama-qwen.service` keeps serving until M6. At the end the migration writes `state.migration.llama_qwen = {state, step, at}` and `state.models.default` itself.

### 4.10 Building llama.cpp (`aictl rebuild-llama`, migration M1)

#### 4.10.1 Inputs
- `commit` = `node.yaml: llama.commit` (or `--commit`), resolved to a full sha.
- `backend` = `node.yaml: llama.backend`.
- **CUDA arch:** `node.yaml: llama.cuda_arch` if set; else `nvidia-smi --query-gpu=compute_cap --format=csv,noheader` → each line `"7.5"` → `"75"`; unique values joined with `;` (multi-GPU). No answer → `LAI-HW-019`, stop.
- Source, first found: `/opt/localai/llama.cpp/src/<commit>/` (already extracted); the legacy checkout (`git archive`, migration only); the kit tarball `<root>/kit/src/llama.cpp-<commit>.tar.gz`, then the kit mirror `<root>/kit/git/llama.cpp.git` (`git archive <commit>`) ([rebuild-kit.md](rebuild-kit.md) §4.3); every source is extracted into `/opt/localai/llama.cpp/src/<commit>/` (the only source location; the installer and the rebuild kit use it too) before the build; online `git clone --filter=blob:none https://github.com/ggml-org/llama.cpp.git` + `git checkout <commit>` (online mode only).

#### 4.10.2 Commands
Build directory `B = /opt/localai/llama.cpp/builds/<build-id>.tmp/build`; output `O = /opt/localai/llama.cpp/builds/<build-id>.tmp`.

Common flags (all backends; matching the source runbook §5 and the ai-n3 build, plus static linking so the result is relocatable — the ai-n3 build today has `RUNPATH=/home/marinoscar/llama.cpp/build-cuda/bin`, which would break under `ProtectHome`):
```
cmake -S /opt/localai/llama.cpp/src/<commit> -B $B -G Ninja \
  -DCMAKE_BUILD_TYPE=Release \
  -DBUILD_SHARED_LIBS=OFF \
  -DLLAMA_CURL=OFF \
  -DLLAMA_BUILD_TESTS=OFF \
  -DLLAMA_BUILD_EXAMPLES=OFF \
  -DGGML_NATIVE=ON \
  <backend flags>
cmake --build $B --config Release --target llama-server llama-cli llama-bench -j <J>
```
`-G Ninja` is always used (`ninja-build` is a build prerequisite on every backend, and is in the kit debs, [rebuild-kit.md](rebuild-kit.md) §4.1.4).

| Backend | Backend flags | Build prerequisites (apt) |
|---|---|---|
| `cuda` | `-DGGML_CUDA=ON -DCMAKE_CUDA_ARCHITECTURES=<arch>` | `build-essential cmake ninja-build git nvidia-cuda-toolkit` (nvcc; ai-n3 has CUDA 12.4 at `/usr/bin/nvcc`) |
| `vulkan` | `-DGGML_VULKAN=ON` | `build-essential cmake ninja-build git libvulkan-dev glslc spirv-headers` |
| `cpu` | none | `build-essential cmake ninja-build git` |

`J = max(1, min(nproc, floor(MemAvailable_GiB / 2)))` (CUDA compilation needs ~2 GiB per job; ai-n3 with ~10 GiB free gets `-j 5`). `GGML_NATIVE=ON` is correct because each node builds for itself; the rebuild kit's portable binaries are specified in [rebuild-kit.md](rebuild-kit.md).

Timeout: 3 h (offline CPU or CUDA builds on a laptop with few parallel jobs can be slow). Output goes to the journal (`component=router.build`, last 200 lines on failure in the error details) and to `$O/build.log`, which moves with the build.

### 4.13 `aictl bench <model>`
Measures throughput and **VRAM** for the catalog's `min_vram_mib` (catalog.md §2 requires a measured value).
1. Preconditions: model present; operator confirms that loaded models will be unloaded (`--yes` to skip). The bench runs in the `aictl` process and drives the agent's load/unload routes, so it cannot hold `modelOpsMu` across the whole run: it refuses to start while a model operation is running, watches `/events` during the run, and marks the result `"disturbed": true` (and does not print a catalog suggestion) if any other model operation happened meanwhile.
2. Unload all models (record them for restore). Sample baseline GPU memory `U0` (5 samples, 1 s apart, median).
3. **VRAM at real context:** load the model with `POST /api/v1/models/{id}/load` (nothing else is loaded, so no eviction). Send one chat completion (`max_tokens: 64`, prompt ~512 tokens) to force KV and compute buffers. Sample GPU memory every 250 ms during the request (in-process, with the same hardware probes the agent uses — not through `GET /hardware?fresh=1`, whose 1-sample-per-2 s limit, [agent.md](agent.md) §3.8.6, does not apply to the bench); `U1` = peak. `measured_vram_mib = U1 − U0`. Also read `GET /models` `memory.effective` when present (recorded, not used).
4. **Throughput:** unload it (`POST …/unload`); run `current/bin/llama-bench -m <weights> -ngl <n_gpu_layers> -fa <flash_attn> -p 512 -n 128 -r 3 -o json` (llama-bench does not exercise speculative decoding, so the speed with MTP/draft is taken from the step 3 response `timings` as `server_tg_tps`, with the draft acceptance from the router log). Timeout 15 min.
5. Restore the previously loaded models.
6. Write `/var/lib/localai/bench/<id>-<ts>.json`:
```json
{"model": "qwen3.5-9b-q4km", "node": "ai-n3", "build": "f3586e66b-cuda", "gpu": "NVIDIA GeForce RTX 2070 with Max-Q Design",
```

### 4.14 Router watcher

An `app.Worker` (`internal/router/watcher.go`, name `router-watcher`). Every 5 s, and whenever the `/models/sse` stream delivers an event (at most one SSE-triggered poll per 500 ms), the agent reads `GET /models` and diffs it with its last view. `Start` returns at once; the first poll runs on the poll goroutine, so a router that is not up yet does not delay the agent.

**The view.** The last good list, when it was read, and `stale` plus the error text when the last poll failed. Readers (`/status`, `GET /models`) copy it under a lock that no I/O ever holds, so a hung router never blocks them. The first good list is a **baseline**: it publishes no event (a model already loaded at start did not just load), but findings are evaluated on it.

**Events** are edge-triggered and published only for changes outside an agent operation, with no `op_id`:

| Change since the last good list | Event |
|---|---|
| a model that was `loaded` or `sleeping` is now anything else (including `loading`: the child restarted) | `model.unloaded {model, reason: "crash"}` |
| a `loaded` or `sleeping` model is no longer in the list (a reload dropped its section) | `model.unloaded {model, reason: "preset_changed"}` |
| a model becomes `loaded` and was not `loaded` or `sleeping` | `model.loaded {model, load_ms}` |

`load_ms` is measured from the first poll that saw the model `loading`; it is `0` when the load was not observed (the duration is unknown, not zero). `loaded` ↔ `sleeping` is not an event. `model.loading` and `model.failed` belong to the orchestrator (§4.4), which knows the `op_id`.

**Operations.** The orchestrator, key rotation and llama restart call `Suppress(op_id)` while they hold `modelOpsMu` and release it when they finish. While any operation is active, the watcher keeps reading but publishes nothing and does not re-evaluate `LAI-LLM-009` and `LAI-LLM-028` (an evict-then-load passes through states that would raise them); what it reads becomes the new baseline, so nothing the operation did is reported later. A poll that overlapped the start or the end of an operation counts as quiet too (an epoch counter, not a timestamp). The release also nudges a poll.

**Findings** are level-triggered: recomputed from every good list, reported once when they appear (`AlertSink.Raise(code, subject, details)`) and cleared when they stop being true (`Clear`). `ManagerAlerts` connects the sink to the doctor alert manager (`internal/doctor`), which owns severity, title, fix and the `alert.raised` / `alert.cleared` events; those alerts are keyed by code, so the adapter raises a code when its first model appears, re-raises it with the new `models` list when the set changes and clears it when the last one is gone.

| Code | Subject | Raised when | Cleared when |
|---|---|---|---|
| `LAI-LLM-009` | model id | the model's `status.failed` is true | it is not |
| `LAI-LLM-028` | none | more models are `loaded` than `models_max` (not evaluated during an operation; skipped when `models_max` is 0) | not any more |
| `LAI-LLM-024` | none | an entry has `source: cache`, or its id is not in the effective set (`models.ini`) | none is left |
| `LAI-LLM-004` | none | 3 consecutive polls fail with the router not answering (connection, timeout, `502/503/504`): a llama restart takes a few seconds and is not an alert | a poll succeeds |
| `LAI-LLM-005` | none | 2 consecutive polls get `401` (the client has already re-read the key file once per call) | a poll succeeds |

A malformed answer, a missing key file or any other failure marks the view stale and is logged once per episode; it raises no code.

**Failures and backoff.** After `n` consecutive failed polls the wait doubles per failure up to 30 s (5, 10, 20, 30, 30 ... s); one success resets it. `Kick()` (a `key.rotated` event, an operation's release, an SSE event) polls at once. When the router comes back after a restart, the next good list is diffed against the last good one: models that were loaded and are not any more are reported as `crash` (unless an operation was running).

**Key rotation.** On `key.rotated` the watcher makes the client forget its cached key and polls. A rotation the watcher did not hear about is absorbed by the client's one retry after a `401` (§3.6.1 rule 2), so it raises nothing.

**SSE.** The stream is only a nudge and a source of load progress; `OnProgress` hands every event to the orchestrator, which forwards `model.loading {progress}` with its own `op_id` (§4.4 step 6), and `LatestProgress(id)` returns the last progress of a loading model. It reconnects with backoff (1 s doubling to 30 s, reset after an event or a 30 s run); an unavailable stream is logged once per episode and the poll carries on alone. A restart of llama ends the stream, which polls at once.

Known limit: a router that restarts and brings the same models back within one poll interval produces no event (the diff sees `loaded` before and after). The orchestrator's own restarts are suppressed anyway, and the unit's `NRestarts` (the service watcher) records the rest.

## 6. Security considerations
- llama-server binds only `127.0.0.1:8080`; children bind random loopback ports and are reachable only from the router (and other local processes; they carry no key — accepted, loopback-only, same trust as before).
- The API key reaches the process only through systemd `LoadCredential` (`%d/llama-api-key`), never on a command line or in an environment variable; `/proc/<pid>/cmdline` shows the credential path, not the key.
- The unit runs as `localai` with no write access outside `/var/lib/localai`.
- `extra_args` cannot override host/port/key/model (catalog lint) and are rendered as INI keys, never through a shell.
- Builds compile third-party code as root into `/opt`; the source comes from a pinned commit (catalog `kit-llama-cpp`, node.yaml `llama.commit`), verified by the kit's sha256 when taken from the kit.
- Migration never prints the key; it logs the fingerprint only.

## 7. Observability
- slog `component=router` with keys `op_id`, `model`, `phase` (`check|plan|evict|load|rollback`), `duration_ms`, `code`; build logs `component=router.build`.
- Events: `model.loading`, `model.loaded`, `model.unloaded`, `model.failed`, `model.default_changed` (agent.md §3.10).
- Counters (in `/status?counters=1` and heartbeat extra): loads ok/failed, mean and last `load_ms` per model, rollbacks.
- llama-server's own logs are in `journalctl -u localai-llama` (children's output goes through the router).
