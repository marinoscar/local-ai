# `laictl`: the cloud app's command line

`laictl` installs, updates and checks the Local AI cloud app (`https://ai.marin.cr`) on the VPS. It also runs the VPS stack-agent and calls the cloud API from any computer.

It is the EnterpriseAppBase `appctl` (`@marinoscar/platform-cli`), renamed so it is never confused with `aictl` on the nodes. Wherever the platform's documentation says `appctl`, run `laictl` (the state folder is `~/.laictl/`, the environment prefix `LAICTL_`). The composition is [`src/app.ts`](src/app.ts).

> **Not the node CLI.** `aictl` runs on the GPU nodes. It is part of the Go agent, and `installers/install-node.sh` installs it from a `node-v*` release. See [runbook 05](../../../../docs/runbooks/05-add-a-node.md) and [aictl.md](../../../../docs/specs/aictl.md).

## Install

You need `git` and Node.js 24 or later (`node -v`).

```bash
curl -fsSL https://raw.githubusercontent.com/marinoscar/local-ai/deploy/cloud/install.sh | bash
laictl --version
```

- **What you should see:** `Installed laictl 0.1.0 (platform …)`, then the same version from `laictl --version`.
- **If it doesn't work:** `laictl: command not found` means `~/.local/bin` is not on your `PATH`. Add `export PATH="$HOME/.local/bin:$PATH"` to `~/.bashrc` and open a new terminal. `Node.js 24 or later is required` means you need to install Node 24 (on Ubuntu: the NodeSource packages or `nvm install 24`).

The installer clones the `deploy/cloud` branch into `~/.laictl/app`, builds the CLI there and writes a small launcher to `~/.local/bin/laictl`. It changes nothing outside those two places.

| Variable | Default | Use |
|---|---|---|
| `INSTALL_REPO` | `https://github.com/marinoscar/local-ai.git` | Clone another fork |
| `INSTALL_REF` | `deploy/cloud` | Another branch or tag (it must have the flat layout, see [below](#why-deploycloud-and-not-main)) |
| `INSTALL_BIN_DIR` | `~/.local/bin` | Put the launcher somewhere else |
| `INSTALL_UNINSTALL` | unset | `1` removes the CLI |

From a clone of the `deploy/cloud` branch you can also run `bash install.sh`, or skip the launcher and use `npm ci --workspace=cli && npm run build --workspace=cli`, then `node apps/cli/dist/cli.js …`.

## Update the CLI

Run the same one-line command again. It fetches the newest `deploy/cloud` and rebuilds.

Update the CLI **before** you run `laictl deploy update`. An older CLI does not know about variables a newer revision requires, and the image build then stops with `required variable … is missing a value`.

## Uninstall the CLI

```bash
curl -fsSL https://raw.githubusercontent.com/marinoscar/local-ai/deploy/cloud/install.sh | INSTALL_UNINSTALL=1 bash
```

This removes `~/.laictl/app` and the launcher. Your stored server URL and token in `~/.laictl/` are kept. A deployed cloud app is not touched; to remove one, use `laictl deploy uninstall`.

## Deploy the cloud app to the VPS

The full operator procedure, with what you should see after each step, is [runbook 10, Part 9](../../../../docs/runbooks/10-lab-operations.md#part-9-deploying-and-updating-the-cloud). The design is [cloud-app.md §3.13](../../../../docs/specs/cloud-app.md#313-deploy-laictl-deploy-to-the-vps). In short, over SSH as `root`, after DNS, the database role and the Google OAuth client are ready (runbook steps 57 to 60):

```bash
# 1. Check the server (Docker, the shared proxy, ports, DNS, certificates)
laictl deploy doctor --domain ai.marin.cr --repo https://github.com/marinoscar/local-ai.git

# 2. First install: asks for the .env values and offers to generate the secrets
laictl deploy install --domain ai.marin.cr \
  --repo https://github.com/marinoscar/local-ai.git --ref deploy/cloud \
  --no-version-bump --name local-ai-cloud

# 3. Later updates: update the CLI first (section above), then
laictl deploy update --name local-ai-cloud --no-version-bump

# Health and inventory
laictl deploy status --name local-ai-cloud
laictl deploy list
```

- `--repo` and `--ref` are needed when you run `laictl` outside a git checkout. Inside a clone of `deploy/cloud` they default to that clone's remote and branch. `deploy install` records them, and `deploy update` reuses them.
- `--no-version-bump`: `deploy/cloud` is generated by CI, so the CLI must not commit a version bump to it. Versions change on `main`.
- **Back up `SECRETS_ENCRYPTION_KEY`** from the deployment's `infra/compose/.env` right after the first install (runbook step 62). Without it, no stored node key can be read again (`LAI-CLD-032`).
- To move the cloud to a newer agent release, change `AIAGENT_VERSION` in the deployment's `infra/compose/.env`, then run `deploy update`.

Run `laictl deploy <command> --help` for every flag. The platform's full deploy guide (proxy modes, database role provisioning, certificates, rollback with `--ref <sha> --force`, the troubleshooting table) is the EnterpriseAppBase [deploy-to-vps runbook](https://github.com/marinoscar/EnterpriseAppBase/blob/main/docs/runbooks/deploy-to-vps.md). Read `appctl` there as `laictl`.

## Other commands

| Command | What it does | Where it is described |
|---|---|---|
| `laictl login --server https://ai.marin.cr` | Authorize this computer (device flow) and store a token | [EAB CLI reference](https://github.com/marinoscar/EnterpriseAppBase/blob/main/apps/cli/README.md) |
| `laictl api <method> <path>` | Call any cloud API endpoint, for example `laictl api GET /api/health/ready` | same |
| `laictl config` | Show the stored server URL and a masked token hint | same |
| `laictl node enroll …` / `laictl node start …` | Run this machine as a worker node of the cloud's job queue. On the VPS this is the **stack-agent** that publishes node endpoints | [runbook 10, Part 10](../../../../docs/runbooks/10-lab-operations.md#part-10-installing-the-vps-stack-agent), [cloud-app.md §4.10](../../../../docs/specs/cloud-app.md) |
| `laictl init` | Write `infra/compose/.env` for local development (`npm run setup` runs it) | [apps/cloud README](../../README.md) |

## Troubleshooting

| You see | Why | Fix |
|---|---|---|
| `npm ci` fails while building the CLI (for example `can only install with an existing package-lock.json`) | `INSTALL_REF` points at `main`, which has the monorepo layout | Leave `INSTALL_REF` unset (it defaults to `deploy/cloud`) |
| `required variable … is missing a value` in `deploy update` | The CLI is older than the revision being deployed | Update the CLI, then `laictl deploy update --name local-ai-cloud --no-version-bump --force` |
| `deploy install` cannot find the repository | You ran it outside a checkout without `--repo` | Add `--repo https://github.com/marinoscar/local-ai.git --ref deploy/cloud` |
| The image build stops with `AIAGENT_VERSION is not set` | The agent release version in `.env` is empty or wrong | Set it to an existing `node-v*` release without the `node-v` prefix, then `deploy update` |
| `LAI-CLD-033` in the cloud Doctor | `aictl` is missing in the API image | `laictl deploy update --name local-ai-cloud --no-version-bump --force` |

Anything else: [07 Troubleshooting](../../../../docs/runbooks/07-troubleshooting.md).

## Why `deploy/cloud` and not `main`

The platform's deploy tooling expects the app at the **root** of a repository. In this monorepo the app lives in `apps/cloud/` of `main`. The workflow `cloud-deploy-branch` (`scripts/cloud-deploy-branch.sh`) copies `apps/cloud` to the branch `deploy/cloud` as a flat tree after every green `cloud-ci` on `main`. Both this installer and `laictl deploy` work from that branch. Never edit `deploy/cloud` by hand. This lasts until upstream seam request SR-3 ([cloud-app.md §3.12](../../../../docs/specs/cloud-app.md)) lets the tooling deploy a subfolder.

A change to this CLI, or to `install.sh`, reaches users only after it is merged to `main` and the workflow has published `deploy/cloud`.
